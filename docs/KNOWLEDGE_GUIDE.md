# 知识库规范作用说明

本说明用于理解知识库中16份文档分别解决什么问题、什么时候使用，以及相近文档之间的分工。
这些文档都是项目自定义的演示规范，不代表真实行业标准。
本说明位于`docs`目录，不属于知识库入库清单，不会作为规范依据参与检索。

## 一、先理解整体关系

可以把知识库看成一套遥感影像成果的操作手册，按下面的顺序阅读：

```text
准备资料与生产
→ 整理成果和说明材料
→ 检查质量并登记问题
→ 处理问题与返工
→ 提交复核并由人判定
→ 判断交付条件、组织交付包和验收
```

其中，DOM可以先理解为本项目需要产出的遥感影像成果；元数据是描述成果身份和属性的说明材料。
质量问题“闭环”是指问题从登记、处理到检查和复核都有可追溯结果。

阅读时可以先按下面的意思理解常见词：

| 词语 | 通俗解释 |
| --- | --- |
| 成果版本 | 同一任务可能多次生成文件，版本用于区分本次和以前的成果 |
| 规范版本 | 说明本次采用哪一版业务要求，与成果版本分别记录 |
| 参数版本 | 说明本次生产使用哪一套处理参数，与成果版本、规范版本分别记录 |
| 控制资料 | 用于定位或检查影像位置的参考资料 |
| 坐标参考 | 说明影像中的位置怎样对应到实际地理位置的依据 |
| 接边 | 相邻影像或区域的边界是否对齐、衔接是否正常 |
| 像元 | 组成影像的一个个小格 |
| 合格限值或阈值 | 项目采用的合格界限，超过允许范围就需要处理 |
| 检查证据 | 能说明检查过程和结果的报告、记录或其他材料 |
| 完整性校验 | 检查文件内容是否与清单登记时一致，不能单独证明影像质量合格 |
| 复核门禁 | 复核通过前必须核对的条件 |

“创建返工”表示已经安排任务；“完成返工”表示已经实际处理并保留记录；“关闭问题”需要检查依据和关闭确认；
“复核通过”则需要复核人员审查后正式确认。这四件事要分别核对。

检查结论还应区分下面三种情况：

| 情况 | 应怎样说明 | 下一步 |
| --- | --- | --- |
| 有足够材料证明要求满足 | 写明满足哪项要求及其证据 | 继续核对其余条件 |
| 有足够材料证明要求未满足 | 指出具体问题、文件或字段 | 处理问题后重新检查 |
| 材料缺失或不能对应当前成果 | 列出缺少或不匹配的材料，说明暂时无法判断 | 补齐材料后再判断 |

材料不足时不能通过，也不能直接写成已经测得质量超限。正式复核若因材料不足驳回，应写明缺少什么。
文档中提到“最近一次复核”，应结合任务号和成果版本理解，不能拿同一任务旧成果的通过记录代替当前成果的复核。

检查和复核按下面的顺序理解：先检查成果并形成报告，再由复核人员审查报告和问题处理材料。
报告形成后仍可能有未关闭问题；问题处理完毕还需复核确认。不能把检查报告已经写好理解为问题已闭环或允许交付。

| 类别 | 文档数量 | 主要回答的问题 |
| --- | ---: | --- |
| 生产与成果管理 | 3 | 开工需要什么、怎样算生产完成、材料怎样整理 |
| 质量检查 | 4 | 检查哪些异常、需要什么证据、问题怎样处理 |
| 坐标系要求与异常处理 | 2 | 坐标信息应满足什么要求、出现问题怎样返工 |
| 复核 | 2 | 提交什么材料、依据什么判定通过或驳回 |
| 交付与验收 | 3 | 能否交付、材料是否齐全、怎样核查验收 |
| 历史版本 | 2 | 过去采用什么规则、当前检索是否误用了旧版 |

## 二、生产与成果管理

### 1. DOM产品生产控制规范

原文：[DOM产品生产控制规范](../knowledge-base/active/dom/dom-production-v2.md)。

**作用：说明生产开始前要准备什么，什么条件下才算生产完成。**

- 检查源影像、控制资料和处理参数是否登记、可用且对应当前任务。
- 核对必需生产步骤及本次输出，防止只完成部分步骤就宣布生产完成。
- 失败后保留步骤、错误和版本信息，重新处理后再次验证成果。

使用场景：用户问“任务已经是COMPLETED，为什么订单还不能交付？”
它提供“生产完成后还要检查质量、复核和交付条件”的解释依据。

### 2. DOM成果元数据规范

原文：[DOM成果元数据规范](../knowledge-base/active/dom/dom-metadata-v2.md)。

**作用：规定一份影像成果的说明材料需要写清哪些信息。**

- 说明成果属于哪个订单、任务、产品和成果版本。
- 记录坐标参考、处理级别和覆盖范围等空间信息。
- 关联质量问题和复核结果，并检查这些信息与成果文件、业务记录是否一致。

使用场景：用户问“这份成果属于哪个任务，坐标信息在哪里，质量记录对应哪个版本？”
它说明应该检查的字段及关联关系；实际字段值仍需从成果材料或业务服务取得。

### 3. DOM成果组织规范

原文：[DOM成果组织规范](../knowledge-base/active/dom/dom-packaging-v2.md)。

**作用：规定文件、目录、命名和清单怎样组织，方便查找及核对。**

- 成果、元数据、质量报告和复核材料按职责分开存放。
- 文件名和清单能够定位到稳定任务标识及准确文件位置。
- 清单与实际文件双向对应，新旧版本明确区分，文件变更后同步更新相关记录。

使用场景：目录里有多版成果和多份报告，无法确定哪份报告对应哪个文件。
这份规范帮助解释怎样整理和追溯材料。

## 三、质量检查

### 4. DOM云量检查规范

原文：[DOM云量检查规范](../knowledge-base/active/quality/cloud-screening-v2.md)。

**作用：说明怎样检查云遮挡对成果使用的影响。**

- 明确检查对象、成果版本和实际检查范围。
- 记录检查方法、异常位置和证据，区分检查通过与没有取得检查结果。
- 按项目要求及问题状态判断，处理后补充证据并重新复核。

使用场景：报告只检查局部区域，用户问“能否认定整幅成果都合格？”
应指出未检查范围，不能扩大局部结论。本演示规范没有设定通用云量百分比阈值。

### 5. DOM几何精度检查规范

原文：[DOM几何精度检查规范](../knowledge-base/active/quality/geometric-accuracy-v2.md)。

**作用：说明怎样检查影像地物位置、接边和异常位移等空间关系。**

- 使用当前成果、适用的控制资料及质量记录。
- 记录比较位置、方法、实际结果和判定依据，不能仅凭外观宣布合格。
- 返工后重新检查受影响范围，并形成新的证据和复核记录。

使用场景：新成果已经替换，但仍引用旧版本的位置精度报告。
应先核对报告是否适用于当前成果。本演示规范没有设定通用米级或像素级阈值。

### 6. DOM辐射质量检查规范

原文：[DOM辐射质量检查规范](../knowledge-base/active/quality/radiometric-quality-v2.md)。

**作用：说明怎样检查影像异常、色调一致性和无效像元等质量问题。**

- 基于当前成果检查，区分成果异常与页面显示异常。
- 异常需有可定位的证据和对应问题记录，不能凭一句描述补造测量值。
- 核对问题关闭和复核结果，涉及影像内容的返工后重新检查。

使用场景：页面显示一块异常区域，用户问“是否能直接认定成果质量有问题？”
应先取得成果本身的检查证据。本演示规范没有设定通用色调差异或异常数量阈值。

### 7. 质检问题闭环规范

原文：[质检问题闭环规范](../knowledge-base/active/quality/quality-issue-handling-v2.md)。

**作用：规定发现质量问题后，怎样跟踪处理、保留证据并重新判断后续条件。**

- 登记问题类型、任务归属、状态、影响范围和异常证据。
- 说明OPEN问题对复核通过和交付的阻断，以及返工任务需要关联的对象。
- 区分创建返工、实际处理、问题关闭和复核通过，避免把一个环节成功当成全部完成。

使用场景：用户问“返工任务已经创建，原问题是不是就解决了？”
创建任务只是安排处理，还需要实际处理结果、检查证据及业务状态确认。

## 四、坐标系要求与异常处理

### 8. DOM坐标参考要求

原文：[DOM坐标参考要求](../knowledge-base/active/coordinate-system/coordinate-reference-v2.md)。

**作用：规定成果应该具备哪些坐标信息，以及不同材料之间怎样保持一致。**

- 声明足以核对的坐标参考、处理参数版本及相关单位等信息。
- 核对成果内部定义、元数据、处理参数和质量报告中的说明。
- 坐标修正后更新成果和关联材料，再提交质量复核。

使用场景：成果内部定义与元数据声明不一致，或坐标信息缺失。
应明确缺失或差异项，不能根据文件名猜测正确值，也不能只改说明文字掩盖成果问题。

### 9. 坐标系异常处理规范

原文：[坐标系异常处理规范](../knowledge-base/active/coordinate-system/coordinate-exception-v2.md)。

**作用：说明发现坐标系异常后，怎样提出返工和后续复核要求。**

- 识别缺失、冲突和版本不一致，关联当前任务及受影响成果。
- 返工建议说明原任务、质量问题、待修正成果及需要补充的检查证据。
- 创建任务后还需实际处理，处理后重新提交复核，不能提前宣布问题关闭或允许交付。

使用场景：ORDER-003存在未关闭坐标系问题，应解释返工目标及为什么还要重新复核。

## 五、人工复核

### 10. 质检复核提交规范

原文：[质检复核提交规范](../knowledge-base/active/review/review-submission-v2.md)。

**作用：说明准备复核申请时，需要哪些材料、怎样描述处理情况。**

- 核对任务、成果版本、问题处理记录和证据的关联关系。
- 如实区分实际处理结果与待处理事项，不能把建议写成已经完成的动作。
- 重新处理后保留新的提交记录及其与历史材料的关系。

使用场景：用户只写“已经修好”，需要解释还应补充什么复核材料。
规范中的PENDING表示等待处理；是否提交成功应以正式受理记录为准。

### 11. 质检复核判定规范

原文：[质检复核判定规范](../knowledge-base/active/review/review-decision-v2.md)。

**作用：为复核人员提供通过、驳回及理由记录的判断依据。**

- 检查最新成果、问题集合、实际处理和重新检查证据。
- 仍有OPEN问题、证据不足或版本不匹配时，不得直接给出通过结论。
- 正式结论须由有职责的复核人员确认，保留审查依据、时间和关联版本。

使用场景：处理说明写着“已修正”，但问题状态仍为OPEN。
应先核对处理证据和实际状态。复核结果写入与创建返工任务需要分别确认。

## 六、交付与验收

### 12. DOM成果交付前置条件

原文：[DOM成果交付前置条件](../knowledge-base/active/delivery/delivery-preconditions-v2.md)。

**作用：判断当前成果是否具备交付条件。**

- 生产任务完成，影响交付的质量问题全部关闭。
- 最新质量复核通过，交付记录未处于BLOCKED状态。
- 各项条件对应同一当前成果，关键事实未知时不能认定允许交付。

使用场景：ORDER-003生产已经完成，但问题仍为OPEN且复核为PENDING。
它提供“仍不满足交付条件”的依据；之后条件变化，需要重新核对正式业务记录再判断。

### 13. DOM交付包组织规范

原文：[DOM交付包组织规范](../knowledge-base/active/delivery/delivery-package-v2.md)。

**作用：检查本次准备交付的一整套材料是否齐全、匹配且符合安全要求。**

- 收齐成果、元数据、质量报告、复核记录和文件清单。
- 检查材料是否属于同一订单、任务及成果版本，清单是否与文件对应。
- 隔离历史版本，排除访问凭据、调试日志及无关沟通记录等内部材料。

使用场景：影像成果已存在，但缺少复核材料，或交付包混入旧版报告。
应说明缺项和版本差异；文件数量相同不能单独证明材料完整。

### 14. DOM成果交付验收规范

原文：[DOM成果交付验收规范](../knowledge-base/active/delivery/delivery-acceptance-v2.md)。

**作用：说明怎样核查拟交付材料，并形成有依据的验收结论。**

- 核对文件完整性、业务标识、成果版本、质量复核和交付前置条件。
- 分别说明已满足、不满足和缺少依据的检查项，失败时定位到具体材料或条件。
- 补齐材料后重新检查并保留记录关系，正式结论由有权限的验收人员依据证据确认。

使用场景：文件都能打开，但最新复核仍为PENDING。
文件完整性不能单独支持整体验收通过，验收责任及确认记录见原文“验收责任”章节。

## 七、历史版本

### 15. DOM坐标参考要求（历史版本）

原文：[旧版DOM坐标参考要求](../knowledge-base/historical/coordinate-system/coordinate-reference-v1.md)。

**作用：回查旧坐标要求，进行版本对比，并验证失效版本过滤。**

- 该版本有效期截至2024年12月31日，已被当前版本替代。
- 旧版允许部分参数在复核阶段补录，这条演示规则已经失效。
- 仅用于明确的历史查询，不能作为当前生产或返工依据。

使用场景：用户明确询问过去采用的坐标规范，或测试检索是否会误用旧条款。

### 16. DOM成果交付前置条件（历史版本）

原文：[旧版DOM成果交付前置条件](../knowledge-base/historical/delivery/delivery-preconditions-v1.md)。

**作用：解释旧交付条件与当前条件的差异，验证系统能否避免误用旧规则。**

- 该版本有效期截至2025年3月31日，已被当前版本替代。
- 旧版以生产完成和交付包完整为主要条件，允许部分问题交付后跟踪；这条规则已经失效。
- 当前交付判断应使用适用的有效版本，不能选择条件较宽松的历史条款。

使用场景：对比历史交付流程，检查旧文档是否被错误地用于当前订单。

## 八、容易混淆的文档分工

| 文档组合 | 各自负责什么 |
| --- | --- |
| 成果元数据、成果组织 | 元数据说明成果身份和属性；成果组织说明目录、文件、清单和版本怎样安排 |
| 云量、几何精度、辐射质量 | 分别关注云影响、空间位置关系和影像内容质量 |
| 单项质量规范、问题闭环规范 | 单项规范给出检查要求；闭环规范说明问题如何登记、处理、追踪和复核 |
| 坐标参考要求、坐标异常处理 | 前者说明应满足什么；后者说明发现异常后如何返工及复核 |
| 复核提交、复核判定 | 前者说明提交材料；后者说明复核人员依据什么作决定 |
| 成果组织、交付包组织 | 前者覆盖文件组织规则；后者核对本次完整交付材料、版本及内部信息排除 |
| 交付前置条件、交付包组织、交付验收 | 分别说明能否交付、材料是否齐全匹配，以及如何逐项核查验收 |

## 九、ORDER-003如何结合这些规范

固定演示场景为：ORDER-003关联TASK-003，生产COMPLETED；ISSUE-001类型为COORDINATE_SYSTEM且状态OPEN；
复核PENDING，交付BLOCKED，阻断阶段QUALITY_REVIEW。实际运行时仍须由Java查询确认，不能把文档示例当成实时数据。

| 已查询到的情况或用户疑问 | 可以提供解释依据的规范 |
| --- | --- |
| 生产已经完成，为什么仍有阻断 | 生产控制、质检问题闭环、交付前置条件 |
| 坐标信息是否满足要求 | 坐标参考要求 |
| 未关闭坐标问题应该如何处理 | 坐标异常处理、质检问题闭环 |
| 处理后准备什么材料重新复核 | 复核提交 |
| 当前是否符合复核通过条件 | 复核判定 |
| 当前是否满足交付条件 | 交付前置条件 |

上表说明文档用途，不保证实际检索每次命中同一组文档；命中结果和引用仍需要验证。

## 十、事实来源与当前实现边界

- Java回答“当前任务和问题是什么状态”；知识规范回答“这些情况应满足什么要求、如何处理”。
- 模型可以整理事实、解释规范和生成建议或草稿；写操作必须人工确认，由Java重新校验后执行。
- 规范要求提供检查证据，不代表项目已经实现自动云量识别、几何测量或辐射检测算法。
- 当前返工链路止于创建待处理任务，实际修正成果、重新生产、完整申请处理及最终验收交付尚未全部接入。
- 文档标识、版本、有效期和权限等信息以[catalog.json](../knowledge-base/catalog.json)为准；目录说明见[知识库README](../knowledge-base/README.md)。

## 十一、知识规范与Agent运行约束的分工

知识库正文面向业务人员，说明应检查什么、提供什么证据、由谁确认及何时允许继续办理。
Java与Python的职责、模型调用限制和当前功能实现状态集中在本说明及项目工程文档中，不作为规范正文入库。

| 内容 | 应放在哪里 | 示例 |
| --- | --- | --- |
| 业务条件与责任 | 知识规范正文，并由适用的业务规则落实 | 未关闭问题阻断交付；验收须由有权限的人员确认 |
| 模型行为要求 | 系统Prompt及调用结果校验 | 仅依据已有事实解释，不补造业务状态 |
| 权限、审批及执行范围 | Tool门禁、Approval服务与Java业务校验 | 限制可执行工具；确认前重新核对权限、状态和版本 |
| 当前实现与未实现能力 | 本说明和项目状态文档 | 返工链路止于创建待处理任务，实际修复及最终交付尚未接入 |

检索返回的文本只提供知识依据，不授予执行权限，也不能修改审批或工具调用条件。
即使没有检索到“人工确认”条款，执行链中的审批与权限门禁仍应生效；Prompt用于说明要求，代码负责实际阻止越权执行。
规范可以包含人工审批等业务制度，这些制度应使用业务语言表达，系统怎样执行这些制度由工程设计和代码说明。
