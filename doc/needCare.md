# Agent 面试关注点

本文件只沉淀已经实现、且对 Agent 岗位面试有实际价值的内容，不作为开发流水账。每个条目只保留项目价值、与 Agent 开发的关系和可据实回答的面试问题；完整筛选门禁由根目录 `AGENTS.md` 维护。

---

## M0.1 服务职责边界

### 解决的问题/对项目的价值

明确 Web 交互层、Python Agent 编排层和 Java 业务事实层的职责，避免模型或编排代码绕过业务权限、状态校验和审计直接访问数据库。M0.1 当时只完成三服务可启动骨架，价值在架构边界而不是 Agent 能力本身。

### 与 Agent 开发的关系

Web 只提供页面上下文和人工交互，Python 负责 Tool、Workflow、RAG 与运行记录，Java 负责可信业务事实和最终写入。页面传入的 `order_id`、`task_id` 和用户信息都只是提示，后端仍需重新校验。

### 可能的面试问题

**为什么不让 Agent 直接查询业务数据库？**

回答要点：直连会绕过权限、状态语义、审计和兼容层，也会让数据库结构变化直接破坏 Agent；稳定的 Java API 才是 Tool 的事实来源。

**为什么 Java 和 Python 要拆成两个服务？**

回答要点：Java 承载已有业务规则和一致性，Python 承载模型生态与编排。拆分的核心是明确事实、决策和写入责任，不是单纯增加技术栈。

## M0.2 领域状态契约与 Agent 事实边界

### 解决的问题/对项目的价值

统一订单、任务、生产步骤、质检、复核和交付的对象及状态，避免 Java、Python 和前端对同一业务状态产生不同解释，为后续 Tool Schema 和确定性诊断提供稳定契约。

### 与 Agent 开发的关系

Agent 只能归纳结构化业务事实，不能补造状态。Java Enum、DTO 和数据库约束共同限定事实范围；Entity 留在持久化层，DTO 才是跨服务接口边界。M0.2 尚未实现 HTTP Tool 调用。

### 可能的面试问题

**领域模型为什么会影响 Agent 可靠性？**

回答要点：Tool Schema 来自领域契约。状态名称或含义不统一时，模型得到的是歧义事实，Prompt 无法弥补底层契约冲突。

**为什么不直接把 JPA Entity 返回给 Agent？**

回答要点：Entity 带有懒加载和持久化语义，可能暴露内部结构、循环引用并随数据库重构变化；DTO 能形成稳定、最小的事实接口。

**数据库约束是否足以保证诊断事实正确？**

回答要点：不足。数据库适合保证枚举、外键和非空，跨对象状态组合仍需 Java 业务规则校验，Agent 只能基于校验后的结果归纳。

## M0.3 确定性业务场景与 Agent 评测基线

### 解决的问题/对项目的价值

用 `ORDER-001`～`ORDER-005` 固定覆盖正常生产、生产失败、质检阻塞、待复核和可交付分支，使 Tool、Workflow 和 Prompt 变更能够在相同事实输入上回归。`ORDER-003` 是质检复核阻塞的黄金链路。

### 与 Agent 开发的关系

固定场景把“Agent 是否正确”从主观观感变成可验证的 Tool 路径、事实覆盖和结论匹配。业务事实不随机、不依赖当前时间，且不预置 `ORDER-003` 的返工任务，避免测试数据提前满足 Agent 应提出的建议。

### 可能的面试问题

**为什么 Agent 项目需要确定性测试数据？**

回答要点：模型输出可能变化，但业务事实和期望分支必须稳定，否则无法区分错误来自模型、Prompt、Tool、数据还是环境。

**五个订单与普通数据库夹具有何区别？**

回答要点：它们同时是业务数据和决策评测集，能够验证 Agent 是否选择正确 Tool、是否遗漏证据、是否补造状态以及是否发生回归。

**如何降低 Agent 幻觉业务事实的风险？**

回答要点：事实只来自 Java Tool；模型只负责路由、归纳和解释；固定场景要求结论可回溯到 Tool 输出，写入还需 Approval 与 Java 再校验。

## M0.4 Java 查询契约与 Tool 事实接口

### 解决的问题/对项目的价值

通过订单、任务、进度、质检、复核和交付查询接口，把数据库中的业务状态转成稳定、可校验的 HTTP 事实契约，并保证 `ORDER-003` 的完整链路可从 Java API 获取。

### 与 Agent 开发的关系

Python Tool 不直接访问业务库，而是消费 Java DTO。接口区分 `404` 与 `200 + []`、对集合稳定排序，并由 Java 执行枚举过滤，使 Workflow 能区分资源错误、确实无记录和真实业务状态。聚合接口服务页面与排障，细粒度接口服务可观测的 Tool 路径。

### 可能的面试问题

**为什么有订单总览接口还要设计细粒度 Tool？**

回答要点：大接口调用少但会隐藏决策路径，单项失败也难定位；细粒度 Tool 能按意图取证、记录步骤并评测路径，最终粒度应结合延迟与可靠性权衡。

**空数组和 404 对 Agent 有什么差别？**

回答要点：空数组是“资源存在但暂无子记录”的业务事实，404 是调用前提不成立；混淆会引发错误重试、漏报或补造数据。

**为什么查询结果要稳定排序？**

回答要点：稳定顺序减少无业务意义的输出变化，有利于 Schema 测试、缓存对比、Workflow 回归和模型结果评测。

## M0.5 Agent 写操作的业务安全边界

### 解决的问题/对项目的价值

为复核草稿保存与人工确认建立 Java 写入边界，通过权限、状态、版本、幂等键和审计约束，防止模型建议未经确认落库、重复提交或覆盖并发修改。

### 与 Agent 开发的关系

Agent 只能生成可审查草稿；真正写入由 Java 在确认时重新校验。幂等键处理网络重放，版本号处理并发状态变化，审计记录保留操作者和请求关联。M0.5 只完成 Java 写 API，完整 Approval Workflow 尚未实现。

### 可能的面试问题

**为什么 Agent 写操作必须经过人工确认？**

回答要点：模型输出不是业务授权，可能错误或过期；确认步骤把建议与执行分开，并让用户审查实际写入内容。

**幂等键和乐观锁分别解决什么问题？**

回答要点：幂等键防止同一操作因重试重复执行，乐观锁防止基于旧状态覆盖新状态，两者不能互相替代。

**确认时为什么还要重新校验？**

回答要点：草稿生成到确认之间，权限和业务状态都可能变化；仅信任生成时检查会产生典型的检查与使用时序风险。

## M0.6 Tool 错误控制流与链路标识

### 解决的问题/对项目的价值

统一 Java API 的成功信封、错误信封、稳定错误码和 Trace ID，让下游能够以机器可读方式区分参数、资源、权限、冲突和服务异常，而不是依赖自然语言报错。

### 与 Agent 开发的关系

Python Client 可将稳定错误码映射为 Tool 异常，Workflow 再决定停止、澄清、重试或失败；Trace ID 将 Web、Python 和 Java 的一次调用关联起来。此阶段建立的是 Java 契约，Python 映射在 M1.2～M1.3 完成。

### 可能的面试问题

**为什么 Agent Tool 不能只看 HTTP 状态码？**

回答要点：同一状态码可能包含不同业务语义；稳定错误码才能支持确定的重试、澄清和终止策略，错误消息只用于解释。

**Trace ID 对 Agent 系统有什么价值？**

回答要点：一次 Agent 请求会跨前端、编排和多个 Tool，Trace ID 能串联调用并定位具体上游失败，同时不等同于 Run ID 或业务 ID。

**为什么异常响应也必须结构化？**

回答要点：结构化错误可被 Client 校验和 Workflow 分支处理，避免模型从异常文本猜测错误类型。

## M0.7 Agent Tool 故障评测夹具

### 解决的问题/对项目的价值

提供仅开发环境可用、可重复触发的延迟与失败注入，解决真实故障难以稳定复现的问题，为后续 Tool 超时、重试、错误映射和 Step 失败记录提供确定性测试条件。

### 与 Agent 开发的关系

故障参数只作用于只读请求，且有环境开关、参数上限和固定错误结构；这样可验证 Agent 控制流而不污染业务数据。它不是生产容错能力，也不覆盖网络分区等全部真实故障。

### 可能的面试问题

**为什么不直接依赖 Mock 测试重试？**

回答要点：Mock 适合单元测试，但真实 HTTP 链路还能暴露超时配置、错误信封和 Trace 传播问题；可控故障夹具补充跨服务验证。

**故障注入为什么只能用于只读接口和开发环境？**

回答要点：写接口注入可能造成副作用不确定，生产暴露故障参数也有安全风险；环境门禁和只读范围限制爆炸半径。

## M1.1 Agent 自有状态边界与最小可观测性

### 解决的问题/对项目的价值

建立 FastAPI、配置、数据库连接、Alembic 和 Trace 日志骨架，使 Python 服务可以独立演进 Agent 自有的 Run、Step、会话等状态，同时保持业务事实仍归 Java 所有。

### 与 Agent 开发的关系

Agent 服务拥有编排状态但不得映射订单、任务、质检等 Java 表；`/health` 只做 liveness，不把数据库可用性伪装成健康。当前本地 Java 与 Python 仍共用开发数据库角色，权限级隔离尚未完成。

### 可能的面试问题

**Agent 服务为什么还需要自己的数据库？**

回答要点：它要保存 Run、Step、会话、消息和未来检索元数据，这些属于编排与可观测性，不是 Java 业务事实。

**代码边界和数据库权限边界有什么区别？**

回答要点：代码约定能防止正常开发误用，独立数据库角色才能在运行时阻断越权访问；当前项目已建立代码边界，权限级隔离仍是后续事项。

**为什么健康检查不查询数据库？**

回答要点：liveness 只判断进程是否存活，依赖就绪应由 readiness 单独表达，避免数据库短暂异常导致进程被错误重启。

## M1.2 Java HTTP Client 事实门禁与跨服务上下文

### 解决的问题/对项目的价值

集中处理 Python 到 Java 的 URL、超时、统一信封校验、Pydantic DTO、错误映射和请求头传播，防止每个 Tool 各自实现 HTTP 细节并产生不一致行为。

### 与 Agent 开发的关系

Client 是业务事实进入 Agent 的门禁：只有状态码、外层信封和内层 DTO 都通过校验的数据才能进入 Workflow；`X-Trace-Id`、用户与权限上下文跨服务透传，但 Java 仍负责最终鉴权。此阶段没有实现动态 Agent 循环。

### 可能的面试问题

**为什么 Java 响应需要多层校验？**

回答要点：HTTP 成功不等于业务成功，业务成功也不等于数据结构正确；必须依次校验状态、信封和 DTO，防止脏数据进入模型上下文。

**为什么把 HTTP 逻辑集中在一个 Client？**

回答要点：统一超时、头传播、反序列化和异常映射，Tool 只表达业务意图，也便于整体替换认证或传输策略。

**用户上下文透传是否代表 Python 已完成鉴权？**

回答要点：不是。Python 传播调用上下文，Java 必须基于可信身份再次校验资源权限，不能盲信页面或模型提供的字段。

## M1.3 面向 Workflow 的标准 Tool 错误语义

### 解决的问题/对项目的价值

把 Java 错误、网络错误和响应校验失败归一为稳定 `ToolError`，再转换为可序列化的 `ToolResult.error`，让 Workflow 不必捕获 httpx、Pydantic 和业务异常的多种细节。

### 与 Agent 开发的关系

异常负责中断 Python 调用栈，`ToolResult.error` 负责在 Workflow、API 和 Step 中传递结构化失败。错误包含类别、可重试性、Trace ID 和必要详情，但会清理敏感上游内容；它建立错误控制流，不代表模型自动修复错误。

### 可能的面试问题

**“Java 错误先变成异常，再变成结果”为什么不是多余转换？**

回答要点：Client 层用异常表达调用失败，Tool 边界将异常收敛成稳定数据结构；前者适合代码控制流，后者适合持久化、API 返回和 Workflow 分支。

**如何决定一个 Tool 错误能否重试？**

回答要点：根据错误语义和操作副作用，而不是只看异常类型；超时或临时上游异常的只读请求可有限重试，参数、权限和资源不存在不应重试。

**为什么不能把上游异常原文全部交给模型？**

回答要点：原文可能包含实现细节或敏感信息，而且文本不稳定；应提供经过白名单化的错误类别和安全摘要。

## M1.4 Tool 基础协议与可信执行边界

### 解决的问题/对项目的价值

定义统一 Tool 名称、描述、输入 Schema、输出 Schema、执行上下文和注册表，使 Tool 能被一致发现、校验、调用和测试，并阻止重复名称或类型错误在运行期悄悄覆盖。

### 与 Agent 开发的关系

`ToolContext` 携带 Run、Trace 和用户上下文，`BaseTool` 统一输入校验与错误收敛，Registry 是可调用 Tool 的白名单。M1.4 建立执行协议，但尚未实现模型动态选择 Tool。

### 可能的面试问题

**Tool Registry 为什么不只是一个字典？**

回答要点：它还承担唯一名称、注册时校验、发现和白名单边界，防止模型调用未授权或未实现的函数。

**为什么 Tool 输入输出必须使用明确 Schema？**

回答要点：Schema 能在业务调用前拒绝无效参数，在结果进入 Workflow 前校验结构，并为模型函数描述、测试和版本管理提供契约。

**ToolContext 为什么不直接混入业务参数？**

回答要点：订单 ID 等是 Tool 业务输入，Trace、Run、身份等是执行上下文；分离可避免模型伪造系统字段并简化审计。

## M1.5 细粒度只读 Tool 与业务事实防串线

### 解决的问题/对项目的价值

实现七个只读 Tool，分别查询订单、任务、进度、质检、复核和交付，并验证响应中的父子 ID 与请求一致，避免错误缓存、上游缺陷或错误调用导致跨订单事实串线。

### 与 Agent 开发的关系

Tool 将 Java DTO 收敛成 Agent 可消费的结构化结果，同时保留空列表与失败的区别。细粒度设计让后续 Workflow 能记录真实取证路径；当前调用仍是确定性的，并非 LLM 自主选择。

### 可能的面试问题

**为什么响应已经来自 Java，还要检查订单和任务 ID？**

回答要点：跨层防御可阻止错误路由、缓存污染或契约缺陷把其他订单事实带入当前 Run，这是防止高风险事实串线的低成本措施。

**Tool 为什么要保留空列表而不是报错？**

回答要点：没有质检问题或复核记录本身可能是有效事实；将其当失败会让 Workflow 错误重试或让模型猜测缺失内容。

**细粒度 Tool 的代价是什么？**

回答要点：调用次数和延迟增加，需要重试预算、重复调用检测和步骤可观测性；收益是路径透明、错误隔离和更精确的上下文。

## M1.6 只读 Tool 的受约束重试与总预算

### 解决的问题/对项目的价值

为明确可重试的只读 Tool 增加有限重试、指数退避和总耗时预算，既吸收瞬时故障，又避免单个 Tool 无限重试拖垮整次 Agent Run。

### 与 Agent 开发的关系

重试依据错误语义、Tool 只读属性和剩余预算共同决定；参数、权限、404、Schema 校验失败不重试，写操作也不复用该策略。当前策略最多额外尝试一次，是阶段性可靠性边界而非通用容错框架。

### 可能的面试问题

**为什么 Agent Tool 重试需要总预算？**

回答要点：一次 Run 可能调用多个 Tool，若各自只限制次数仍会叠加高延迟；总预算把局部重试纳入用户请求的整体响应时间约束。

**哪些错误不应该重试？**

回答要点：参数、权限、资源不存在和响应 Schema 错误通常不会因等待而恢复；盲目重试只会增加负载并掩盖真实问题。

**读请求可重试是否意味着绝对安全？**

回答要点：仍需确认接口语义无副作用并控制流量；“GET”只是信号，不能替代对实际操作的判断。

## M1.7 Run 内 Tool 重复调用检测

### 解决的问题/对项目的价值

对同一 Run 内相同 Tool 和规范化参数的重复调用进行检测并拒绝，防止 Agent 循环、重复取证和无意义重试浪费延迟与上游配额，同时允许显式强制刷新。

### 与 Agent 开发的关系

检测键由 Tool 名称和规范化参数组成，作用域限定在 Run。命中后返回重复调用错误而不是复用旧结果，因此它是循环保护，不是缓存；需要最新数据时使用 `force_refresh` 或新的业务步骤。当前状态仅在进程内，未实现跨实例共享。

### 可能的面试问题

**重复调用检测是否直接返回第一次结果？**

回答要点：不是。当前实现拒绝重复调用以暴露潜在循环；缓存复用会引入新鲜度、权限和错误缓存语义，需要独立设计。

**如果业务确实需要查询最新数据怎么办？**

回答要点：显式声明 `force_refresh`，让刷新意图可观察、可审计；或者进入新的 Run。不能通过偷偷改变无关参数绕过检测。

**为什么作用域是 Run 而不是全局？**

回答要点：不同 Run 可能代表不同用户、时间和业务状态，全局去重会错误复用旧事实并造成跨请求污染。

## M1.8 开发专用 Tool 调试 API

### 解决的问题/对项目的价值

提供开发环境专用的 Tool 列表与调用入口，让单个 Tool 的 Schema、上下文传播、错误映射、重试和重复调用行为可以脱离完整 Agent 独立验证。

### 与 Agent 开发的关系

调试 API 复用正式 Registry 和执行协议，不建立旁路；环境门禁默认关闭，防止任意调用能力暴露到生产。它是开发诊断面，不是面向最终用户的 Agent API，也不等同于生产级鉴权。

### 可能的面试问题

**为什么需要 Tool 调试接口，pytest 不够吗？**

回答要点：测试验证预设断言，调试接口便于人工观察真实 HTTP 信封、Trace 和错误路径；两者互补，且调试入口必须复用正式执行链。

**如何避免调试接口成为安全后门？**

回答要点：默认关闭、仅开发环境启用、限制为已注册 Tool，并且仍执行 Schema 与上下文规则；生产若需类似能力应另做认证、授权和审计。

**Tool 在哪里注册？**

回答要点：各 Tool 由统一构建函数创建并加入 Registry，API 只查询和调用 Registry，不直接实例化任意类，因此可调用集合是明确白名单。

## M2.1 Agent Run/Step 持久化与可观测性基础

### 解决的问题/对项目的价值

建立 Session、Message、Run 和 Step 的持久化模型，为一次 Agent 请求的上下文、执行状态、步骤证据和耗时提供可查询的数据基础，而不是只依赖临时日志。

### 与 Agent 开发的关系

这些表只保存 Agent 自有元数据与受控快照，不复制 Java 业务实体。Run 表示整次请求，Step 表示内部动作，Session/Message 为后续多轮上下文留出边界；M2.1 只建立数据结构，生命周期操作在后续阶段完成。

### 可能的面试问题

**为什么既要日志又要 Run/Step 表？**

回答要点：日志适合排障和全文检索，Run/Step 是结构化业务级执行记录，可稳定查询状态、耗时、步骤和结果，两者用途不同。

**为什么不把完整 Tool 响应都存进 Step？**

回答要点：完整响应可能含敏感数据且体积不可控；应保存定位问题所需的受控摘要、引用和标识，事实原文仍由权威系统管理。

**Agent 表为什么不能映射 Java 订单表？**

回答要点：否则 Python 会形成第二业务事实源并绕过 Java 规则；Agent 数据库只负责编排历史和可观测性。

## M2.2 Run 状态机、并发终态与结果快照

### 解决的问题/对项目的价值

实现 Run 的创建、成功和失败生命周期，并用条件更新保护终态，防止并发完成、超时回调或重复请求互相覆盖；成功结果和失败位置以受控快照保存。

### 与 Agent 开发的关系

Run 是一次 Agent 执行的顶层可观测单元，终态只能从 `RUNNING` 转到 `SUCCEEDED` 或 `FAILED`。并发终态冲突会被显式报告，而不是最后写入者静默获胜；当前状态机仍是最小集合，未包含取消、恢复和超时等完整生产状态。

### 可能的面试问题

**为什么 Run 完成不能简单执行一次 UPDATE？**

回答要点：多个异步路径可能同时结束同一 Run；带当前状态条件的原子更新才能保证单一终态并发现竞争。

**Run 的结果快照与 Java 业务事实是什么关系？**

回答要点：快照记录当时 Agent 使用和生成的受控结果，便于审计与复现；它不是最新业务状态，也不能替代 Java 查询。

**失败为什么要保存失败步骤？**

回答要点：只记录“Run 失败”无法区分 Tool、规则或持久化问题，失败位置能缩小排障范围并支持阶段性指标。

---

## M2.3 Step 执行证据、摘要最小化与父 Run 一致性

### 解决的问题/对项目的价值

记录每个 Step 的开始、成功、失败、耗时和受控摘要，并校验父 Run 处于可执行状态，使 Workflow 的内部执行路径可审计且不会在终态 Run 下继续追加步骤。

### 与 Agent 开发的关系

Step 将 Tool 调用和规则判断变成结构化证据；输入输出经过深度、数量、字符串长度和敏感键限制，避免把 Token、原始大响应或隐私数据直接持久化。当前实现不承诺进程崩溃后的自动恢复或 exactly-once 执行。

### 可能的面试问题

**Step 为什么只存摘要？**

回答要点：可观测性需要足够定位信息，但完整上下文会带来敏感信息、存储成本和上下文泄露风险；摘要策略是在诊断价值与数据最小化之间取舍。

**为什么创建 Step 时要检查父 Run？**

回答要点：终态 Run 再产生步骤会破坏执行历史的一致性；父子状态校验把非法生命周期尽早拒绝。

**Step 记录是否保证 Tool 只执行一次？**

回答要点：不保证。记录执行证据与 exactly-once 是不同问题；进程崩溃和事务边界仍需幂等、恢复或任务队列机制解决。

---

## M2.4 结构化诊断契约与 Tool 证据边界

### 解决的问题/对项目的价值

定义诊断状态、阻塞阶段、证据、根因、建议和完整结果的 Pydantic Schema，使规则、Workflow、API 和未来模型输出共享同一结构化契约，并对重复证据和非法组合进行校验。

### 与 Agent 开发的关系

诊断结论不能只是一段自然语言：每个根因和建议都应关联可追溯的 Tool 证据。Schema 将业务事实与解释分开，减少幻觉并便于前端展示和自动评测；M2.4 仅建立契约，实际取证和规则绑定由 M2.5～M2.6 完成。

### 可能的面试问题

**为什么 Agent 输出还需要严格 Schema？**

回答要点：Schema 能约束字段、枚举和引用关系，让前端、持久化和评测稳定消费；自然语言保留给解释，不承担控制契约。

**证据引用如何降低幻觉？**

回答要点：结论必须指向 Tool 类型、资源 ID 和事实摘要，评测可以检查引用是否真实存在；但 Schema 只能约束形式，仍需 Workflow 验证证据来源。

**为什么建议也要关联证据？**

回答要点：建议如果脱离当前状态容易变成通用话术或危险操作，关联证据能说明触发条件并支持人工审查。

## M2.5 固定 Workflow：确定性取证、失败中断与 Step 短事务

### 解决的问题/对项目的价值

实现面向订单诊断的固定 LangGraph 取证链，按确定顺序调用订单、任务、进度、质检、复核和交付 Tool；任一步骤失败立即停止，并同步记录 Run 与 Step。

### 与 Agent 开发的关系

固定 Workflow 先验证数据流、错误流和可观测性，再引入动态模型决策。每个节点采用短事务，避免在 HTTP 调用期间占用数据库事务；Tool 失败被持久化为 Step/Run 失败而不是让模型忽略。该阶段尚未包含 LLM 路由、checkpointer、对外诊断 API 或前端 E2E。

### 可能的面试问题

**为什么先做确定性 Workflow，再做动态 Agent？**

回答要点：固定图能先验证 Tool、状态、持久化和错误边界，出现问题时容易定位；动态决策应建立在已可信的执行底座上。

**为什么不能在数据库事务里调用 HTTP Tool？**

回答要点：网络延迟和重试会拉长事务、占用连接并增加锁竞争；应在短事务中记录开始，事务外调用 Tool，再用短事务记录结果。

**Tool 失败后为什么立即中断？**

回答要点：缺少关键事实时继续生成诊断会诱发模型补造；当前里程碑选择 fail-closed，未来若降级必须明确哪些结论仍有充分证据。

## M2.6 确定性规则：模型前置事实裁决与信息不足门禁

### 解决的问题/对项目的价值

把五个固定订单的阻塞阶段和诊断状态交给确定性规则裁决，并对缺失、冲突或未知事实返回 `INSUFFICIENT_INFORMATION`，避免模型在证据不足时强行给出确定结论。

### 与 Agent 开发的关系

规则层消费 M2.5 收集的 Tool 事实，只生成受 M2.4 Schema 约束的 `RuleDecision` 阻塞阶段，不提前生成根因、证据和建议。确定性业务规则放在模型之前，M2.7再负责完整结果装配与可选表达整理；该阶段尚未完成诊断API、前端Agent交互或真实LLM评测。

### 可能的面试问题

**为什么不让 LLM 直接判断订单阻塞阶段？**

回答要点：固定状态组合适合可测试规则，交给模型会增加非确定性和幻觉；模型更适合解释规则结果、处理自然语言意图和选择查询路径。

**为什么需要 `INSUFFICIENT_INFORMATION`，不能选择最可能的结论吗？**

回答要点：业务诊断中的错误确定性比明确未知更危险；缺失关键记录或状态冲突时应暴露证据不足，触发补查、澄清或人工处理。

**规则如何避免退化成难维护的大量 if/else？**

回答要点：先将 Tool 结果归一为有限事实，再按优先级评估互斥状态并输出统一 Schema；随着规则增长可拆分规则对象或决策表，但当前没有过度声称通用规则引擎。

## M2.7 诊断文案：受保护事实与模型失败回退

### 解决的问题/对项目的价值

把确定性阶段裁决装配为包含阶段说明、根因、字段证据和建议的完整结果；即使模型不可用或输出无效，
仍能返回可测试、可追溯的规则诊断，避免自然语言能力成为黄金链路的单点故障。

### 与 Agent 开发的关系

模型只接收规则结果并返回`DiagnosisNarrative`，Schema中没有订单ID、阻塞阶段、证据值或置信度；
合并前还要求根因code和建议action type与规则结果顺序一致。模型失败以LLM Step记录，但不会污染
业务错误通道或覆盖规则结果。当前完成的是供应商无关接口和Workflow集成，尚未接入具体模型客户端、
Prompt版本管理或真实模型评测；M2.8已在此基础上提供诊断API。

### 可能的面试问题

**如何保证LLM只润色文案而不能篡改业务事实？**

回答要点：先由规则生成完整可信结果；模型输出Schema只暴露可改写文本和稳定code；合并时校验code
集合与顺序，并始终复用规则结果中的订单、阶段、证据和置信度。

**模型调用失败为什么不让整个诊断失败？**

回答要点：模型只增强表达，不参与事实裁决；失败应留下可观测的LLM Step，同时回退已验证的规则结果。
如果模型未来参与不可替代的判断，则应改为显式失败而不是沿用这套降级策略。

## M2.8 诊断 API：请求级运行闭环与错误收口

### 解决的问题/对项目的价值

把诊断从内部Workflow变成可演示的HTTP能力，并让每次请求都有Session、Message、Run和Step归属。
成功保存当时的诊断快照，失败保存稳定错误码与失败步骤，避免接口响应与运行记录脱节。

### 与 Agent 开发的关系

API在执行网络Tool前提交RUNNING Run，Workflow节点再通过短事务记录Step；Java等待期间不持有长事务。
标准Tool失败从`StepError`映射到HTTP和FAILED Run，未预期异常统一收敛为安全错误。当前一次性Session
只解决Run外键与请求追踪，不等同于M3多轮会话；身份Header也是最小上下文，不等同于完整认证。

### 可能的面试问题

**为什么必须先提交RUNNING Run再调用Workflow？**

回答要点：Step记录使用独立数据库连接和短事务，只有父Run已经提交且为RUNNING时才能建立外键并
通过状态门禁；若把创建Run和网络调用放进一个长事务，其他连接既看不到父Run又会增加锁占用。

**Tool失败如何同时保持HTTP语义和运行可观测性？**

回答要点：Workflow保存结构化`StepError`并停止下游，应用服务先把Run标为FAILED，再按错误码映射
HTTP状态；响应只含安全字段，原始异常和业务响应不进入错误体。

---

## M2.9 前端诊断呈现：保留事实边界与请求归属

### 解决的问题/对项目的价值

让用户在订单业务页直接审查诊断结论、稳定根因、Tool字段路径和值以及处理建议，同时展示Run、Trace和
失败步骤。订单切换会使在途响应失效，避免把旧订单诊断错误展示到新订单上下文。

### 与 Agent 开发的关系

前端保持Python诊断契约中的稳定code与字段级证据，不把自然语言摘要伪装成业务事实；建议区域明确标记
“仅建议，未执行”，守住后续Approval前不能写入的边界。浏览器只通过同源代理携带当前阶段的演示身份，
运行时响应仍需Schema校验；这不是认证、多轮会话或动态模型路由。

### 可能的面试问题

**前端为什么还要校验Agent成功响应，而不是直接相信TypeScript类型？**

回答要点：TypeScript只约束编译期，网络JSON可能因版本漂移、代理错误或上游缺字段而失真；运行时校验
能阻止伪成功结果进入页面，并转成可观察的`RESPONSE_VALIDATION_ERROR`。

**切换订单时如何避免旧诊断污染当前页面？**

回答要点：提交时捕获订单ID和单调递增请求序号；订单变化会推进序号并清空状态，只有序号和订单ID仍
匹配的响应才能写入结果。底层请求即使不能取消，也不会跨上下文展示。

---

## M2.10 跨服务E2E：证明Agent结论来自真实事实链路

### 解决的问题/对项目的价值

把固定数据、Java接口、Python Client/Tool、Workflow、API和Run/Step持久化放在同一条可重复验收链路，
覆盖五种正常阶段和404、超时、非法响应，避免各层Mock彼此一致但真实系统无法协作。

### 与 Agent 开发的关系

测试不仅断言最终文案，还核对严格Schema、Tool证据来源、全部Tool Step、Run终态和失败位置。超时与
非法响应通过测试边界向真实Java注入既有演示故障，不修改生产Agent接口，保持故障能力和业务能力隔离。

### 可能的面试问题

**Agent E2E为什么既要检查最终阶段，也要检查Run、Step和Evidence？**

回答要点：阶段正确只能说明最终值碰巧符合预期；Step证明实际调用链和失败位置，Evidence证明结论引用
真实Tool字段，Run快照证明响应与审计终态一致，三者共同约束模型或编排层不能绕过事实来源。

**怎样测试真实上游超时而不污染生产API？**

回答要点：启动启用演示故障的隔离Java实例，在测试专用HTTP Transport中注入故障Header；生产诊断路由
不接收该Header，Java默认也关闭故障开关，测试结束删除容器和数据卷。

## M3.1 页面上下文：提示可用但不可信

### 解决的问题/对项目的价值

让用户从订单、任务或质检页面发起诊断时不必重复输入业务标识，同时阻止篡改页面请求后跨订单、跨任务
引用资源。上下文成为提升交互效率的入口，但不能绕过服务端事实和权限边界。

### 与 Agent 开发的关系

前端Adapter负责把页面对象归一为严格`PageContext`；Python先校验顶层订单、上下文订单及角色一致性，
再通过Java只读Tool加载事实并校验任务和质检问题归属，之后才允许规则裁决。`batch_id`和
`satellite_type`因当前Java事实契约无法验证而只保留为提示，不参与诊断。当前Header角色门禁是开发期
最小策略，不等同于完整认证；后续会话和路由只能继承经过同类重校验的业务对象。

### 可能的面试问题

**为什么页面上下文不能直接作为Agent的业务事实？**

回答要点：浏览器参数可被篡改，也可能因页面缓存而过期；它只能帮助选择待查询对象。服务端必须用可信
身份和Java Tool响应确认资源存在、父子归属及当前状态，模型和规则才能消费这些事实。

**上下文伪造为什么分两阶段拦截？**

回答要点：顶层订单或角色不一致无需访问上游，应尽早拒绝；任务、质检问题及产品归属需要Java事实才能
判断，因此在只读事实加载后、规则裁决前检查。这样既减少无效调用，也不让客户端决定业务关系。

---

## M3.2 会话上下文：可继承但必须过期和重校验

### 解决的问题/对项目的价值

让用户后续说“继续检查这个订单”时可以沿用当前业务对象，避免每轮重复提交完整参数；同时限制会话只
保存有界业务引用，通过用户所有权和过期时间防止跨用户读取或无限沿用陈旧上下文。

### 与 Agent 开发的关系

`SessionContext`保存的是指代记忆，不是业务事实缓存。诊断从会话恢复订单或任务后仍进入M3.1页面校验
和Java Tool事实链。每轮原子锁定会话、追加消息序号、创建Run并更新最近诊断Run，避免并发请求产生
重复序号。待确认操作仅保存草稿结构，不等同于Approval；候选对象和已确认参数有数量与类型上限。

### 可能的面试问题

**为什么会话中只保存业务引用，而不缓存完整Tool响应？**

回答要点：业务状态会变化，缓存完整响应容易把历史事实误当当前事实，也扩大敏感数据和版本兼容成本；
会话只解决“用户指的是谁”，执行时重新调用Java Tool确认“它现在是什么状态”。

**滑动过期与会话所有权如何参与诊断门禁？**

回答要点：服务端以`expires_at`判断有效性，诊断和上下文更新会延长TTL，单纯读取不会；复用会话前在同一
事务中锁定会话并校验`user_id`，跨用户或过期请求在创建Message和Run前失败。

---

## M3.3 意图定义：模型输出先成为受控决策再允许分发

### 解决的问题/对项目的价值

把自然语言路由可能产生的意图、业务实体、缺失参数和澄清状态约束为稳定机器契约，避免模型输出任意
Skill名称、遗漏必填参数或把无法识别的问题直接送入业务Tool。

### 与 Agent 开发的关系

意图目录独立声明必填参数和目标业务Skill，`RouterResult`只接受有界实体并验证`missing_fields`与实际
缺参完全一致。`UNKNOWN`没有Skill映射、必须澄清且不可分发；当前只建立模型输出后的确定性门禁，尚未
实现Prompt、模型调用和置信度阈值策略。

### 可能的面试问题

**为什么不让模型直接返回要调用的Skill字符串？**

回答要点：自由字符串容易产生不存在或越权的执行目标；模型只返回有限`Intent`，服务端再通过只读目录
映射到允许的Skill，并检查必填参数和澄清状态，执行面由代码控制。

**`UNKNOWN`为什么需要同时“无Skill映射”和“强制澄清”？**

回答要点：只设置低置信度仍可能被调用方误分发；无Skill从能力目录切断执行目标，强制澄清从状态契约
阻止继续执行，两层约束让未知输入稳定失败而不是猜测业务动作。

---

## M3.4 路由 Prompt：上下文是数据，模型输出必须可验证

### 解决的问题/对项目的价值

把页面、会话和用户消息作为数据注入路由模型，降低Prompt注入影响，并阻止Markdown说明、计划外字段或
错误缺参进入后续业务分发；模型不可用时仍返回稳定可处理结果。

### 与 Agent 开发的关系

System Prompt由代码意图目录生成并带版本，模型适配器同时接收`RouterResult` JSON Schema。所有上下文先
经过Pydantic边界再编码为JSON数据；模型输出由服务端重新解析。只对Schema失败重试一次，且不把原始
输出放入重试Prompt或日志，模型异常和二次失败统一回退无实体`UNKNOWN`。

联动关系：
SessionContext
    ↓ 帮助补全对话语义
Router
    ↓ 选出候选意图和参数
Skill / Workflow
    ↓ 调用 Java Tool
business-service
    ↓ 返回真实业务事实

### 可能的面试问题

**为什么重试时不把完整ValidationError和原始模型输出重新放进Prompt？**

回答要点：原始输出可能包含用户注入内容、供应商细节或敏感信息；固定纠错指令足以表达格式要求，同时
避免扩大Prompt注入和日志泄露面。重试次数限制为一次，防止成本和延迟失控。

**为什么模型调用异常不和Schema失败一样重试？**

回答要点：本阶段只授权一次格式纠错；供应商超时、配额或网络重试需要独立的可观测策略和预算，直接复用
Schema重试会混淆失败类型。当前安全回退`UNKNOWN`，后续再按模型客户端策略显式扩展。

---

## M3.5 参数合并：模型提取与可信来源分离

### 解决的问题/对项目的价值

避免模型把页面或历史会话中的参数包装成“用户本轮明确输入”，并让每个最终实体都能解释来自本轮消息、
已确认会话、当前页面还是临时候选；冲突不再依赖模型临场选择。

### 与 Agent 开发的关系

模型返回的`RouterResult.entities`只允许包含本轮消息实体，并由`EntityExtractionResult`收口；服务端把
各通道候选重新按目标字段校验，再按固定优先级合并。不同值保留为`EntityConflict`；同一最高优先级有
多个值时输出未解析字段，留给M3.6澄清状态机，而不是让低优先级上下文或模型猜测覆盖。

### 可能的面试问题

**为什么实体来源不能由模型自己返回？**

回答要点：模型同时看见用户、页面和会话载荷，自报来源无法证明值真的来自对应通道；由服务端分别接收
各通道并赋予来源，才能保证优先级不可被模型篡改，同时便于审计冲突和解释最终选择。

**为什么检测到不同值后仍允许高优先级值直接胜出？**

回答要点：优先级本身就是确定性用户语义，例如本轮明确订单应覆盖旧页面；只有最高优先级内部仍有多个
不同值时才无法确定。所有差异仍保存在冲突记录中，执行前业务对象还必须由Java Tool重校验。

---

## M3.6 澄清门禁：模型置信度不能直接决定执行

### 解决的问题/对项目的价值

把高、中、低置信度、实体冲突和必填参数统一收口为服务端决策，避免模型高分但缺参、低分却被误分发，
并让用户补参或选择候选后可以继续原意图而不重复承担一次模型不确定性。

### 与 Agent 开发的关系

`RoutingDecision`独立重算缺参并验证`READY`条件，澄清原因和中文问题由确定性模板生成。实体还必须在本轮
用户原文中找到证据，防止模型复制PageContext后伪装为最高来源。用户选择通过字段Schema复验并升级为
`USER_MESSAGE`，随后重新运行同一门禁；当前只恢复内部决策，持久化路由Run和HTTP交互仍未接入。

### 可能的面试问题

**为什么不能只用模型返回的`need_clarification`决定是否追问？**

回答要点：模型可能漏报缺参、忽略候选冲突或给出不稳定置信度；服务端必须从意图目录、合并实体和固定阈值
重新判断。模型的澄清标记只能增加门禁，不能取消代码发现的缺参或冲突。

**用户选择候选后为什么不重新调用模型？**

回答要点：待解决的是一个明确字段，不是重新理解整句话；把选择按字段Schema校验并标记为用户本轮确认，
再恢复原意图可减少延迟和漂移。若仍有其他冲突或中低置信度，确定性门禁会继续要求澄清。

## M3.7 路由评测：指标必须来自固定数据和真实Subject

### 解决的问题/对项目的价值

把自然语言路由从“看几个示例觉得可用”升级为固定数据、可重复执行和可定位失败的工程能力，同时避免在
没有具体模型时用测试替身的满分冒充真实准确率。

### 与 Agent 开发的关系

60条JSONL样本覆盖意图、上下文继承、缺参、候选冲突和澄清状态，`RouterEvaluationSubject`把评测器与
模型Provider解耦。执行器同时比较意图、来源合并后的实体、最终决策和澄清原因；失败文件主动排除用户原文
和上下文。别名样本故意保留“高分二号”到`GF-2`的期望，用于暴露当前字面证据策略的真实缺口。

### 可能的面试问题

**为什么参数完整率使用最终实体精确匹配，而不是只检查必填字段非空？**

回答要点：只检查非空会漏掉错订单、额外幻觉实体和上下文合并错误；精确比较期望非空实体可以同时惩罚
漏参、错参和多造参数。业务事实仍需Java Tool验证，评测这里只判断路由参数是否符合固定期望。

**为什么失败样本不直接保存完整用户消息？**

回答要点：评测失败文件可能进入CI产物或被长期保存，复制消息和上下文会扩大敏感数据暴露面；固定用例ID
已经可以回查受控数据集，失败文件只需保存结构化差异。真实线上样本需另行设计脱敏、权限和保留策略。

## M4.2 知识库数据模型：把RAG适用范围变成可校验数据

### 解决的问题/对项目的价值

规范版本、有效期、产品适用范围和权限不再隐藏在文件名或Prompt中，而是由严格Schema与数据库约束共同
保存；历史规范不能被当作当前依据，为后续可追溯引用和安全过滤建立基础。

### 与 Agent 开发的关系

RAG并非只有Embedding相似度。`knowledge_documents`承载检索前必须执行的生命周期、版本和权限过滤，
`knowledge_chunks`承载章节路径、正文、向量与全文检索信号；业务事实仍只由Java Tool提供。当前只建设
存储契约，尚未声称已经能检索或生成规范结论。

### 可能的面试问题

**为什么文档元数据既要Pydantic校验，还要数据库Check Constraint？**

回答要点：Pydantic在加载入口提供清晰错误和跨文档关系校验；数据库约束保护所有写入路径和并发场景。
两层职责互补，数据库不适合验证完整目录图，应用校验也不能替代持久化一致性。

**为什么M4.2阶段没有立即固定向量维度？**

回答要点：M4.2尚未选择Embedding Provider和模型，提前写死维度会把未作出的供应商决策固化进迁移。
当时用无维度`VECTOR`验证存储能力；M4.4选定首个模型契约后已通过迁移固定为1536维，距离索引仍由后续
向量检索阶段建设。

## M4.3 确定性分块：让RAG引用在重新处理后仍可追踪

### 解决的问题/对项目的价值

同一份规范在不同操作系统或重复运行时会得到相同内容哈希、章节路径和Chunk ID；插入无关章节不会让原有
章节标识整体漂移，从而为Embedding重用、引用回查和增量索引建立稳定基础。

### 与 Agent 开发的关系

Loader不读取业务表，也不让模型决定文档格式或切分位置。格式由扩展名注册表选择，Markdown标题由代码解析，
超长章节按固定边界切分；重复检测发生在数据库和模型调用之前。近似token数仅用于当前分块元数据，不能冒充
具体Embedding模型的真实tokenizer结果。

### 可能的面试问题

**为什么Chunk ID不能只使用`document_id + chunk_index`？**

回答要点：在文档前部插入一个章节会使后续索引全部变化，导致Embedding缓存和历史引用整体失效。当前ID由
文档ID、章节路径、内容哈希及同内容出现序号生成，位置只用于排序，不参与稳定身份。

**为什么要在哈希前规范化BOM和换行符？**

回答要点：Git、编辑器和操作系统可能让同一正文表现为LF、CRLF或带BOM；直接按原始字节哈希会误判为新文档。
先做最小文本规范化可以消除非语义差异，同时不改写正文措辞或标题结构。

## M4.4 Embedding入库：向量空间身份与原子重建

### 解决的问题/对项目的价值

将Provider、模型、1536维度和索引版本作为一个不可拆分的身份保存，避免模型切换后旧向量和新向量被静默
混用；重新索引只有在全部批次生成成功后才进入数据库事务，防止可检索数据处于部分更新状态。

### 与 Agent 开发的关系

模型只负责生成向量，代码负责批次、错误分类、重试预算、响应校验和Chunk身份关联。Provider通过协议可替换，
首个OpenAI兼容适配器不记录密钥或原始错误响应；数据库固定向量维度并记录索引身份，为后续RAG检索、版本
迁移和引用可追踪性提供边界。当前没有真实Provider质量指标，也没有把相似度结果当作规范结论。

### 可能的面试问题

**为什么Embedding重试不能覆盖所有错误？**

回答要点：超时、网络、429和5xx通常是瞬时故障，可以有限退避；认证、非法请求和响应Schema错误重试不会
自行恢复，只会增加成本与延迟。每次重试还需记录批次、版本和稳定错误码，但不能泄露密钥或供应商正文。

**为什么要同时保存模型、维度和索引版本？**

回答要点：相同维度不代表相同向量空间，仅保存维度无法识别模型或预处理变化；显式版本能判断哪些文档需要
重建，并防止查询向量与文档向量来自不同索引契约。

**为什么先生成全部向量再开启数据库写入？**

回答要点：外部模型调用慢且可能重试，长时间占用数据库事务会放大锁和连接压力；全部批次成功后再短事务
替换Chunk，可以避免Provider失败留下部分新向量。若数据量扩大，应改为带staging版本的分段写入和原子切换。

## M4.5 中文关键词检索：让分词策略成为可测试契约

### 解决的问题/对项目的价值

PostgreSQL `simple`配置会把连续中文当成一个词元，直接查询较短短语无法命中长句。当前在应用层保存原文的
同时追加中文双字词元，使章节和正文能够进入GIN全文索引，并对查询长度、词元数和无效单字进行确定性限制。

### 与 Agent 开发的关系

关键词召回不交给模型猜测，也不把用户输入拼成`to_tsquery`语法；应用生成安全词元，数据库只负责匹配和
排名。返回结果保留Chunk、章节、内容哈希和独立关键词分数，后续RRF可以审查每个候选来自哪个检索通道。
当前双字方法优先可重复和无外部依赖，真实中文检索质量仍需在固定数据集上与专业分词方案比较。

### 可能的面试问题

**为什么只做查询预处理还不够？**

回答要点：文档端原始连续中文在`simple`配置中仍是一个长词元，查询端拆成双字后不会自动命中；入库端和
查询端必须共享词元规则。当前通过`search_document`保存原文、章节和双字词元，再生成`tsvector`。

**为什么不用用户输入直接构造`to_tsquery`？**

回答要点：`to_tsquery`要求调用方处理操作符和语法，用户输入可能导致语法错误或改变查询含义；当前先生成
受控词元，再交给`plainto_tsquery`按普通文本处理，SQL参数仍由驱动绑定。

## M4.6 向量检索：距离方向、索引身份和召回边界

### 解决的问题/对项目的价值

统一“余弦距离越小”和“相似度越大”两套方向，对外只暴露`1 - distance`分数；查询还必须与文档的Provider、
模型、维度和索引版本完全一致，避免数值合法但语义空间不同的向量被错误比较。

### 与 Agent 开发的关系

Query Embedding复用文档生成的Provider契约和瞬时错误重试，Repository负责维度、有限性、零向量、TopK和
阈值门禁。SQL按余弦距离升序保留HNSW索引可用性，再把相似度返回给后续混合检索。当前HNSW属于近似召回，
没有真实Embedding数据时不声明召回率或延迟指标。

### 可能的面试问题

**为什么向量查询必须过滤index_version？**

回答要点：相同模型名和维度也可能因分块、预处理或Provider版本变化形成不同索引；跨版本余弦分数不可直接
比较。Query携带完整索引身份，数据库文档字段必须全部一致才能参与候选集合。

**为什么ORDER BY使用distance升序，而不是similarity降序？**

回答要点：两者数学上等价，但pgvector的HNSW索引依赖距离操作符的升序近邻形式；先按`<=>`距离升序让索引
可用，再在SELECT中返回`1 - distance`，兼顾数据库执行计划和上层统一分数语义。

## M4.7 元数据过滤：在相似度之前收紧事实边界

### 解决的问题/对项目的价值

相似内容可能属于不同产品、卫星、规范版本或有效期；仅靠关键词分数和向量相似度会把“语义相关但业务
不适用”的Chunk带入候选。统一过滤契约让生效时间和权限范围成为必填条件，并默认只检索当前有效规范。

### 与 Agent 开发的关系

RAG候选是模型形成规范结论的上游事实边界。关键词与向量Repository复用同一组SQL条件，并在排序和TopK前
过滤，避免模型看到跨产品、历史或无权限内容，也避免某条召回通道绕过安全约束。当前权限枚举只有一个值，
跨权限数据隔离仍需后续权限模型扩展后补充验证；历史审计查询也不属于当前默认检索契约。

### 可能的面试问题

**为什么元数据过滤必须发生在TopK之前？**

回答要点：如果先取TopK再过滤，不适用文档会占满候选名额，导致相关且合法的文档无法进入结果；权限过滤
还可能让未经授权内容先被读取到应用层。把条件下推SQL能同时保证召回完整性和最小数据暴露。

**为什么`effective_at`和`permission_scope`不提供默认值？**

回答要点：默认当前日期会让测试和历史重放不可重复，缺省权限则可能形成fail-open。要求调用方显式提供
这两个上下文，能让每次检索的时效和授权边界可审查、可复现。

---

## M4.8 混合检索：用排名融合隔离分数量纲

### 解决的问题/对项目的价值

关键词相关度和余弦相似度不是同一量纲，直接相加需要依赖数据集校准且容易被某一路分数范围支配。RRF只
使用各通道名次，使第一版混合排序确定、可重复，并让同时被两路命中的Chunk获得更高优先级。

### 与 Agent 开发的关系

融合层只消费已经通过元数据过滤的候选，不把模型引入排序，也不改变规范适用范围。同一Chunk跨通道去重，
冲突载荷关闭失败；连续片段在TopK前合并并保留全部身份和通道信号，为后续Rerank与引用组装提供可审查输入。
当前固定`k=60`尚未经过真实语料评测，调用方也仍需决定每路候选池大小。

### 可能的面试问题

**为什么第一版使用RRF，而不是直接加权关键词分数和向量相似度？**

回答要点：两路原始分数范围和分布不同，权重需要真实数据校准；RRF只依赖稳定名次，不要求先归一化，且
自然提升两路共同命中的结果。代价是丢失分数间距信息，因此仍保留原始分数供后续评测和Rerank使用。

**为什么相邻片段合并要发生在最终TopK之前？**

回答要点：超长章节可能被拆成多个连续Chunk，若先截断TopK，它们会重复占位并挤掉其他文档；先按文档、
章节和连续索引合并能恢复阅读上下文。不同章节或不连续片段不合并，避免把无关正文拼成伪造语境。

---

## M4.9 Rerank：把不可信模型限制为候选打分器

### 解决的问题/对项目的价值

RRF能稳定融合两个召回通道，却不能针对当前自然语言问题判断最终语义相关性。Rerank只允许模型为既有候选
打0～1分，并要求身份唯一、完整覆盖和严格结构；低于阈值的内容在上下文组装前被拦截。

### 与 Agent 开发的关系

模型不能新增规范片段、改变元数据权限或覆盖原始召回证据，只能调整已授权候选的顺序。超时返回带降级原因
的原RRF结果且不使用未知分数过滤；非超时故障和结构异常关闭失败。当前尚未接入具体供应商，0.5默认阈值
也需要后续固定语料评测校准。

### 可能的面试问题

**为什么超时降级时不继续执行低相关阈值过滤？**

回答要点：阈值属于模型分数空间，超时后没有可信分数；用RRF分数代替会混淆量纲并可能误删有效候选。
因此降级明确保留原RRF结果并标记`TIMEOUT`，让下游决定是否继续、提示降级或拒绝生成。

**为什么模型必须返回全部候选，而不是只返回它认为相关的片段？**

回答要点：完整的一一映射能区分“低分”与“漏返回/结构故障”，也能拒绝模型新增未知身份；筛选策略由
确定性服务根据显式阈值执行，而不是把安全边界隐含在供应商输出中。

---

## M4.10 引用结构：合并上下文仍保留逐Chunk证据

### 解决的问题/对项目的价值

相邻Chunk合并能恢复阅读上下文，但如果引用只保存一个新身份，就无法回查每段来源。Citation同时保留
规范名称、版本、章节、主Chunk、全部Chunk身份和原文，使回答依据可以被页面和后续评测逐级追溯。

### 与 Agent 开发的关系

模型生成的文字不是规范事实，带版本和Chunk身份的检索结果才是规范依据。引用结构不接受模型新增正文，
也不拿RRF分数填充缺失的Rerank分数；前端展开的是后端返回的受控原文，而不是重新请求任意文件路径。

### 可能的面试问题

**为什么Citation同时保留`chunk_id`和`chunk_ids`？**

回答要点：`chunk_id`提供稳定主身份供模型和页面引用，`chunk_ids`保留相邻片段合并前的完整来源集合；主身份
必须等于集合首项，既方便简洁引用，也不会牺牲逐Chunk审计能力。

## M4.11 规范问答：用固定图约束检索增强生成

### 解决的问题/对项目的价值

把查询、元数据、召回、重排、充足性和生成变成固定节点，避免模型自行决定是否绕过权限过滤、是否跳过
重排或在没有规范依据时继续回答。不同安全失败使用稳定状态，调用方可以明确展示而不是解析自由文本。

### 与 Agent 开发的关系

`SpecificationSkill`只接受READY的`SPEC_QA`决策；日期和权限显式传入，页面元数据只能收窄候选。回答模型
只能选择后端生成的引用ID，未知引用、无结果、Rerank超时和生成异常都不能形成规范结论。当前没有具体模型
Provider或HTTP入口；M4.12只建立检索评测框架，真实回答质量仍需具体模型、声明级引用覆盖和事实一致性评测。

### 可能的面试问题

**为什么Rerank超时时规范问答选择安全回答，而M4.9本身会返回原RRF候选？**

回答要点：M4.9是通用组件，只负责保留可降级候选并公开状态；规范结论风险更高，M4.11作为下游策略层要求
低相关门禁已经完成，因此发现降级后不把未经精排的候选交给生成模型。

**如何防止模型伪造一个看似合法的引用？**

回答要点：模型只返回主Chunk ID，服务端要求ID唯一且属于本轮已授权、已重排候选，再从后端Citation映射中
装配最终引用；模型不能提交文档名、版本、章节或正文覆盖权威载荷。

## M4.12 RAG评测：用同一标注和指标比较检索策略

### 解决的问题/对项目的价值

把50条规范问题固定标注到预期文档和完整章节路径，让关键词、向量、RRF和Rerank变更可以在同一输入与
相关性定义下回归。Hit@5衡量是否召回，MRR衡量首个相关片段是否靠前，无关片段占比衡量送入下游的噪声。

### 与 Agent 开发的关系

RAG质量不仅影响回答完整性，也决定模型接触多少无关上下文。评测复用生产日期、权限和产品/卫星过滤契约，
失败文件不保存问题与正文；Rerank超时降级会终止该策略评测，避免把RRF回退结果记成模型重排效果。当前
可控Subject验证的是评测框架和数学，不代表尚未接入的真实Embedding或Reranker质量。

### 可能的面试问题

**为什么相关性要求文档ID和完整章节路径同时命中？**

回答要点：只命中文档可能返回同规范中的无关章节，仍会污染生成上下文；完整路径命中更接近可引用证据，
也能把“文档找对但定位不准”稳定归为章节失败。

**Hit@5、MRR和无关片段占比分别解决什么问题？**

回答要点：Hit@5回答Top5里有没有正确证据，MRR关注第一条正确证据的位置，无关片段占比衡量总体噪声；三者
组合才能区分完全漏召回、排序靠后和候选污染，不能用单一命中率代替。

## M5.1 Agent State：把动态循环变成可审查状态

### 解决的问题/对项目的价值

动态Agent如果只保留当前模型输出，就无法可靠判断是否重复调用、是否持续获得新事实以及为什么停止。
扩展状态把动作观察、信息缺口、迭代次数和终止原因显式化，使后续决策与限额能够基于结构化历史执行。

### 与 Agent 开发的关系

Observation只保存参数SHA-256指纹和安全摘要，业务事实仍由既有强类型Tool字段承载；成功、失败和新增信息
标记具有确定性一致性约束，`FINISH`也不能伪装成Tool观察。本阶段只建立状态与序列化边界，尚未实现模型
动作输出、动态LangGraph循环或限额执行。

### 可能的面试问题

**为什么Tool History不直接保存完整Tool请求和响应？**

回答要点：动态循环只需要稳定识别调用、判断成败和是否获得新信息；完整业务响应会复制Java权威事实、
扩大敏感数据与持久化边界。参数指纹支持后续重复检测，强类型事实字段支持规则判断，安全摘要用于可观测性。

**为什么同时需要Information Gaps和Termination Reason？**

回答要点：Information Gaps描述当前还缺什么，是下一步动作选择的输入；Termination Reason解释为什么不再
继续，是循环出口的审计结果。两者分开才能区分“信息已经充分”和“信息仍不足但预算已耗尽”。

---

## M5.2 动作模型：模型提议与确定性执行解耦

### 解决的问题/对项目的价值

让模型只负责从已知事实中提议下一步只读动作，而不是直接调用任意Tool。动作、执行器和参数必须通过唯一
映射、Pydantic参数Schema、当前Registry与状态资源身份校验，错误输出不会变成可执行请求。

### 与 Agent 开发的关系

Prompt把Java事实、Observation、Information Gap和实际可用Tool目录作为受控JSON数据注入，并明确禁止写入、
编造标识和把摘要覆盖成事实。结构非法时只纠错一次；未知、未注册、非LOW风险动作或模型异常返回空参数
`FINISH`。本阶段没有执行动作，权限、重复调用和预算仍由后续动态图与限制节点确定性处理。

### 可能的面试问题

**为什么模型输出通过ActionDecision后还要查询ToolRegistry？**

回答要点：静态Schema只能证明名称和参数形状符合代码目录，不能证明该实例当前真的注册或仍是LOW风险Tool；
Registry复核把部署时可用性和真实输入Schema纳入门禁，防止配置漂移让合法JSON变成不可执行或越权调用。

**为什么非法动作只重试一次并回退FINISH？**

回答要点：一次纠错能处理常见格式偏差，继续无限重试会增加成本并可能形成失控循环；安全`FINISH`不调用Tool、
不生成业务结论，让后续完成节点以信息不足结束，而不是猜测模型原意或选择默认业务查询。

---

## M5.3 LangGraph动态图：让模型规划与确定性执行形成闭环

### 解决的问题/对项目的价值

把独立的动作决策接入可回环状态图，每轮都经过校验、执行、Observation保存和完成判断。模型不能直接修改
业务事实，失败也不会穿过正常结果分支，从而让动态路径既有灵活选择能力，又保留可审查的执行边界。

### 与 Agent 开发的关系

`plan_next_action`只接收结构化动作；`validate_action`再次检查Registry、LOW风险、参数Schema和资源归属；
`execute_action`通过BaseTool权限与响应门禁获得Java事实，规范问答则显式携带日期和权限并独立保存。
`check_completion`和两个结束节点用规则确定是否可以形成结论。M5.4已在这条循环上增加决策轮、Tool数、
重复调用和连续无新增信息限制。

### 可能的面试问题

**为什么ActionDecider已经校验过，图中还需要validate_action节点？**

回答要点：决策层校验用于拒绝不合法模型输出，执行前校验是独立的纵深防御和清晰审计节点；它基于执行时
Registry和最新状态再次确认风险、参数及资源归属，避免决策与执行之间的配置或状态变化直接变成Tool调用。

**规范检索结果为什么不直接合并进订单业务事实或根因？**

回答要点：Java Tool是订单状态、任务和质检事实的权威来源，RAG只提供带版本引用的规范依据。两者独立保存
可以防止规范文本被误当成“该订单确实发生了什么”，后续只能用规范解释或支撑建议，不能覆盖业务事实。

---

## M5.4 Agent执行限制：为动态循环安装确定性保险丝

### 解决的问题/对项目的价值

即使模型一直不返回`FINISH`、反复选择同一调用或持续得到相同结果，动态图也必须在固定预算内结束。限制层
把轮次、Tool调用、指纹、新信息和权限变成代码可验证的硬边界，避免仅依赖Prompt自律控制成本与安全。

### 与 Agent 开发的关系

模型调用前检查6轮决策预算，Tool执行前检查8次调用预算、动作白名单、Registry、LOW风险、参数、资源和权限，
Observation保存后检查连续2次无新增信息。预算类终止保留已有事实生成诊断；非法动作和缺权属于执行边界
破坏，进入异常安全出口。`iteration_count`计算所有模型决策，`FINISH`不产生Tool Observation。

### 可能的面试问题

**为什么最大决策轮数和最大Tool调用数要分开？**

回答要点：一次决策可能是`FINISH`，也可能在执行前因重复、权限或预算被拦截；两者分别度量模型推理成本与
外部系统调用成本。即使当前默认6轮使8次Tool上限通常不可达，独立边界仍能保护配置调整和未来非一对一动作。

**为什么重复调用在动态图中拦截，BaseTool已经有Run内去重还不够吗？**

回答要点：BaseTool去重是所有调用方共享的最后防线，会返回`DUPLICATE_CALL`；动态图提前识别相同指纹可直接
以`NO_NEW_INFORMATION`解释循环终止，不产生一次失败Tool Observation，也避免把可预测的规划问题交给执行层。

---

## M5.5 信息充分度判断：把“还缺什么”变成确定性状态

### 解决的问题/对项目的价值

动态Agent如果只凭模型判断信息是否充分, 容易缺少关键事实时提前作结论, 或机械查询所有Tool。场景化缺口
规则让生产、质检、复核、交付和规范要求都由代码计算, 并保留稳定代码供Prompt、测试和终止审计使用。

### 与 Agent 开发的关系

`InformationGapDetector`在初始化和每次Observation后运行, 校验Java事实归属及嵌套完整性, 再把缺口传入
下一轮动作Prompt。模型仍可选择查询顺序, 但不能决定缺口是否消失；`FINISH`和预算终止只有在缺口清空时才
允许动态规则形成场景结论。规范问答的安全无结论响应只证明检索已经尝试, 不会被合并成业务事实或规范结论。

### 可能的面试问题

**为什么不用一套固定字段清单判断所有订单的信息充分度？**

回答要点：生产中的订单只需生产进度即可确认最早阻塞, 强制查询质检和复核会增加无效调用；而质检或复核
场景缺少对应事实又会误报。基础要求加场景规则既保留可靠性, 又按最早业务阶段控制Tool成本。

**为什么空质检问题列表可以表示信息充分, 空字典却不可以？**

回答要点：`quality_issues[task_id] = []`表示Tool已经查询并确认该任务没有问题；字典中没有`task_id`表示尚未
查询。区分“已知为空”和“未知”可以避免把默认空容器误当成真实的无问题结论。

## M5.6 动态路径测试：用业务场景验收Agent闭环

### 解决的问题/对项目的价值

单元测试能证明节点和规则各自正确, 但不能证明模型动作、Tool门禁、事实合并、Information Gap与结果生成
组合后仍正确。五订单路径把动态Agent作为完整系统验收, 并用固定Workflow结果防止灵活路径改变业务结论。

### 与 Agent 开发的关系

参数化测试为每个订单提供受控动作序列, 断言真实HTTP路径、Observation顺序、缺口清空、终止原因和完整
`DiagnosisResult`。超时测试穿过Business Client错误映射、BaseTool重试和动态图Observation保存, 证明一次
逻辑Tool动作可以包含有限物理重试, 但Agent历史仍只记录一次动作。

### 可能的面试问题

**为什么动态结果要和固定Workflow比较完整对象, 而不只比较blocking_stage？**

回答要点：阶段相同仍可能丢失根因、证据或建议, 也可能出现字段来源漂移。完整对象对齐同时保护阶段优先级、
稳定代码、字段级证据和建议边界, 更能证明动态路径只是减少无关查询而没有改变业务语义。

**Tool内部重试为什么不能增加Agent的Tool历史或决策轮数？**

回答要点：重试是一次逻辑调用中的传输恢复, 输入和业务意图没有变化；如果把每次物理尝试写成Agent动作,
会扭曲调用预算、重复检测和模型历史。只有最终Tool结果形成一条Observation, 重试次数通过日志记录。

## M5.7 版本记录：让Agent结果可以追溯到当时的执行契约

### 解决的问题/对项目的价值

只保存Run结果无法解释同一输入在组件升级前后为何不同。版本快照把Router Prompt、Agent Prompt、模型配置、
Tool Schema和RAG策略绑定到Run, 使回归差异可以先按契约版本定位, 又避免保存密钥、完整Prompt或Tool响应。

### 与 Agent 开发的关系

应用启动时从代码常量、受控配置与真实Tool注册表构建快照, Run创建时复制并持久化；Tool契约同时保存人工
版本和确定性SHA-256摘要, 能发现忘记手工升版的Schema变化。未接入决策模型时显式记录`configured=false`,
迁移前Run使用`UNAVAILABLE_LEGACY`, 不用当前版本伪造历史。Run终态更新白名单不包含版本字段。

### 可能的面试问题

**为什么Tool Schema既要人工版本号, 又要内容摘要？**

回答要点：人工版本便于沟通发布语义, 但维护者可能忘记升版；对排序后的输入/输出Schema、安全等级和权限计算
摘要可以自动识别真实契约变化。两者并存兼顾可读性与防漂移能力。

**为什么旧Run不直接回填迁移时的当前版本？**

回答要点：数据库迁移只能知道“现在”的代码, 无法证明旧Run执行时使用的版本。回填当前值会制造错误审计
证据；明确标记不可恢复虽然信息更少, 但保持事实边界诚实。

## M6.1 Approval 数据模型：隔离模型建议与业务写入

### 解决的问题/对项目的价值

模型可以生成复核或返工建议，但建议不能直接等同于用户授权。Approval把写操作意图保存为独立记录，冻结
原始内容、目标对象版本和待调用Tool，同时保留用户修改及确认事实，使写入前后都能回答“模型建议了什么、
用户改了什么、确认了什么”。

### 与 Agent 开发的关系

Approval位于动态Agent和Java写Tool之间，不承载Java业务事实，也不在草稿或确认阶段调用写接口。生命周期
服务用显式状态图和数据库比较更新限制执行资格；操作类型与Tool映射同时由服务校验和数据库约束保护，目标
版本留给执行前Java重新校验。Run删除只解除来源关联，避免运行清理连带删除人工确认审计证据。

### 可能的面试问题

**为什么必须分别保存原始草稿和用户修改，不能只保留最后版本？**

回答要点：最后版本只能证明将要执行什么，无法证明模型原先建议与用户实际授权的差异；分开保存可以审查
修改责任、定位生成质量问题，并让执行侧优先使用用户副本而不覆盖原始证据。

**Java写接口已有幂等和版本校验，为什么还需要Approval状态机？**

回答要点：Java校验保护业务事实的一致性，Approval保护人机授权过程；两者边界不同。状态机阻止未确认草稿、
重复确认和并发状态覆盖进入执行，Java仍需在真正写入时重新校验权限、状态和目标版本。

## M6.2 复核草稿 Schema：让生成和人工编辑共享同一安全契约

### 解决的问题/对项目的价值

结构化输出不等于业务有效输出。ReviewDraft把最终结论、文本长度、规范引用和返工建议变成代码可验证规则，
并在原始草稿和用户修改两个入口执行相同校验，避免用户编辑绕过模型输出门禁或确认旧目标之外的任务。

### 与 Agent 开发的关系

Schema复用RAG Citation而不是只保存模型生成的引用字符串，因此每条规范依据仍携带文档、版本、章节和Chunk
身份。Approval生命周期把草稿解析为不可变模型后再持久化，并将草稿`task_id`绑定到独立保存的`target_id`；草稿的
`issue_id`还要由生成Workflow绑定到最新Java质检问题集合，用户修改时两个影响对象都不能替换；
Schema负责结构真实性，后续Workflow和Java分别负责引用当前有效性及业务事实一致性。

### 可能的面试问题

**为什么复核草稿要复用完整Citation，而不是只保存规范ID？**

回答要点：规范ID只能定位文档，不能证明生成结论使用了哪个版本、章节和Chunk；完整Citation可以直接展示和
审计，也能复用RAG已有的主Chunk、来源去重和版本格式校验，避免两套引用结构发生漂移。

**ReviewDraft已经校验task_id格式，为什么生命周期还要比较Approval target_id？**

回答要点：格式正确只证明它像一个任务ID，不证明它就是用户正在确认的目标。独立比较可以阻止编辑请求把
`TASK-003`替换成另一个合法任务，从而保证展示对象、版本快照和最终写入对象始终绑定。

## M6.3 草稿生成 Workflow：旧诊断只作线索，确认草稿必须基于最新事实

### 解决的问题/对项目的价值

诊断结果是历史快照，规范也可能换版；直接把两者复制成待确认草稿会产生典型的检查与使用时序风险。M6.3在草稿
生成时重新读取任务版本与质检问题，并重新执行带日期、权限和引用的规范检索，使人工看到的建议建立在生成时刻
可验证的事实和依据上。

### 与 Agent 开发的关系

Workflow把模型限制在强类型事实和RAG Citation白名单内，模型没有Tool入口，输出还要经过ReviewDraft、目标任务、质检问题
和完整引用一致性校验。只有全部门禁通过后，Approval与来源Run才在同一事务进入等待确认；若诊断已被使用、
Java只读Tool失败、任务串线、RAG无现行依据或模型输出异常，都不会留下可确认草稿，更不会调用Java写接口。

### 可能的面试问题

**为什么生成Approval草稿时还要重新查询Java，不能直接使用诊断Run里的证据？**

回答要点：Run保存的是诊断当时的执行证据，不是持续更新的业务事实；任务版本和质检状态可能已经改变。草稿生成
前强制刷新可以降低旧建议进入人工确认的概率，但最终执行前仍要再次查询和比较版本，分别防住生成期与执行期的
时序变化。

**为什么草稿模型只能引用RAG返回的完整Citation，而不能只让它输出规范名称？**

回答要点：规范名称无法证明版本、章节和原始Chunk，模型也可能创造不存在的依据。引用白名单同时比较文档、版本、
Chunk集合和完整内容，既阻止新增引用，也阻止拿真实ID替换正文；没有现行引用时直接停止生成。

## M6.4 前端确认卡片：让用户授权的是可见、可修改的完整草稿

### 解决的问题/对项目的价值

人工确认不能只是一个“同意”按钮，否则用户无法判断写入对象、版本、实际意见和依据是否正确。确认卡片把目标任务、
质检问题、版本、问题摘要、可编辑结论与意见以及RAG规范引用放在同一审查界面，并用二次确认和提交锁减少误触与重复操作。

### 与 Agent 开发的关系

组件接收Approval和强类型ReviewDraft，在浏览器内只维护编辑副本；结论变化会确定性同步返工建议，最终只向父级发出
确认或取消事件。它不把点击直接等同于业务成功，也不调用Java写Tool；服务端仍需校验草稿、记录授权事实，并在执行
前重新检查权限、状态、目标版本和引用适用性，使前端防重复与后端幂等、状态机各自保护不同边界。

### 可能的面试问题

**前端已经禁用按钮防重复，为什么后端仍必须做状态比较和幂等？**

回答要点：按钮锁只能限制当前页面实例，无法阻止刷新、多标签页、网络重放或并发客户端。前端防重复改善交互并减少
无效请求，Approval状态比较保护授权流程，Java幂等和版本校验保护最终业务事实，三层不能互相替代。

**为什么确认卡片展示目标版本和规范原文，而不只展示Agent总结？**

回答要点：总结是模型归纳，不是授权证据；目标版本帮助用户识别草稿是否可能过期，完整Citation让用户核对文档版本、
章节和原始片段。页面提供可审查信息，但执行前仍要由服务端重新校验动态事实。

## M6.5 写 Tool：让已确认内容成为唯一可执行参数源

### 解决的问题/对项目的价值

人工确认如果只发生在页面，而写Tool仍接受任务、问题、意见和版本等自由参数，就存在“看见的是A、写入的是B”的授权
绕过风险。M6.5把复核和返工写入都绑定到`EXECUTING` Approval快照，并用Java幂等键、乐观锁版本和响应归属校验共同
保护最终业务写入。

### 与 Agent 开发的关系

动态Agent不能取得写Tool注册表，也不能拼装Java写请求；确定性执行链只能用`approval_id`选择已经人工确认的快照，
再由Tool映射业务参数。Python验证授权过程和响应契约，Java重新保护业务权限、状态、版本与幂等，执行结果通过比较
更新只保存一次；这体现了“模型提出建议、人工授权、确定性代码执行、业务服务裁决”的分层边界。

### 可能的面试问题

**为什么写Tool输入只有approval_id和idempotency_key，不直接接收task_id、issue_id和review_comment？**

回答要点：这些字段已经是用户确认内容，再开放给调用方会产生第二个参数来源，无法证明实际写入与授权画面一致。
Approval是唯一快照，幂等键只控制同一写请求的安全重放；执行前仍要由服务端重新校验快照和最新Java事实。

**为什么写Tool设置max_retries=0，Java却仍要求幂等键？**

回答要点：应用层自动重试会放大写操作风险，因此Tool不自行重试；但客户端超时可能发生在Java已经提交之后，用户或
上层执行链仍可能重放同一请求。Java幂等键保证重放返回第一次业务结果，Python比较时忽略每次HTTP都会变化的Trace，
但绝不接受不同业务结果覆盖首次执行证据。

## M6.6 确认前重新校验：把一次页面点击变成唯一且基于最新事实的业务执行

### 解决的问题/对项目的价值

确认卡片展示的是某个时刻的任务版本和问题状态，用户阅读期间业务数据仍可能变化；前端按钮锁也无法覆盖刷新、
多标签页、网络重放和多个客户端。M6.6在写入前重新读取Java事实，并用数据库比较更新决定唯一执行者，使过期草稿、
业务变化和重复提交都不会静默变成新的业务记录。

### 与 Agent 开发的关系

确认服务把模型建议与业务执行之间的时间窗口显式建模：模型草稿只提供候选内容，当前用户再次授权后，确定性代码
验证有效期、确认人、任务版本、任务状态和质检问题，再把唯一锁定的Approval交给高风险写Tool。只读上游失败时保留
`CONFIRMED`供安全重试，业务变化进入`STALE`，Java仍负责最终权限、版本、幂等和事务一致性；当前流程不重新运行RAG。

### 可能的面试问题

**为什么前端已经防重复点击，服务端还要用CONFIRMED到EXECUTING的CAS？**

回答要点：前端锁只约束单个组件实例，刷新、多标签页、请求重放或两个客户端仍可并发提交。CAS把“谁有资格执行”
交给数据库原子裁决，失败请求即使完成了只读重校验也拿不到写Tool；Java幂等继续保护锁后网络不确定性，两层职责不同。

**为什么先重新查询Java再抢执行锁，而不是先锁住再查询？**

回答要点：只读查询可能超时或上游暂不可用，过早进入`EXECUTING`会把可重试的确认卡在执行态。先刷新事实让查询失败
时保留`CONFIRMED`，随后用短CAS抢锁；查询和写入之间仍可能发生极短竞态，因此Java还必须比较版本，若返回409则将
Approval标记为`STALE`。

**重复请求为什么有时返回执行中冲突，有时直接返回第一次成功结果？**

回答要点：并发请求在首个请求完成前看到`EXECUTING`，此时不能假装已经成功；首个请求完成后，后续同确认人、同草稿
请求可以从`execution_result`恢复严格结果并返回，而不再次调用Java。这样既不虚报进行中的结果，也让安全重放可用。

## M6.7 操作日志：同时保留模型建议、人工修改和确定性执行结果

### 解决的问题/对项目的价值

只保存Java成功结果无法回答“用户到底修改了模型草稿的哪些字段”，只保存完整请求又会复制长篇规范正文和扩大敏感
数据面。M6.7使用受控写前/写后摘要和字段级差异，把一次人工授权的来源、变化、结果与Java Trace关联起来；失败写入
也保留机器摘要，并通过唯一约束防止重复点击生成多条互相矛盾的审计记录。

### 与 Agent 开发的关系

Agent系统需要解释的不只是模型输出，还包括模型建议如何被人工修正、确定性代码最终执行了什么。日志构建器比较原始
草稿和有效草稿，引用只保留可定位身份，终态和日志在同一事务提交；Java自己的`operation_logs`继续记录权威业务事务，
Agent的`agent_operation_logs`记录授权与编排证据，两者职责隔离而能通过Java Trace关联。

### 可能的面试问题

**为什么不直接复用Java已有的operation_logs？**

回答要点：Java日志与业务写入同事务，记录权威业务前后状态；Agent日志记录模型草稿、用户修改和Approval身份。复用会让
Agent直接依赖Java业务表并混淆数据所有权，而且公共Schema中同名表会产生迁移冲突，因此物理表使用Agent前缀隔离。

**为什么操作日志要和Approval终态放在同一事务，而Java结果已由写Tool先保存？**

回答要点：执行结果解决幂等重放，操作日志解决可审查性；如果先把Approval标成成功再写日志，日志失败会形成不可解释的
成功记录。同事务保证终态与审计证据同成同败，Java侧幂等继续保护跨服务写入已经成功但Agent事务尚未完成的窗口。

**字段差异为什么不直接保存两份完整JSON？**

回答要点：完整JSON重复数据、包含长引用正文且不便审查。稳定字段路径能直接表达人工改动，写前摘要保留最终授权内容，
规范引用压缩为文档/版本/Chunk身份；原始完整草稿仍由Approval保存，需要时可以关联但不会在日志中再次扩散。

## M7.1 Run完整字段：把一次Agent执行变成可比较的请求级证据

### 解决的问题/对项目的价值

只保存最终答案和错误码，无法快速判断结果差异来自页面上下文、路由、组件版本、资源消耗还是终止条件。完整Run把
安全上下文快照、可选路由结果、版本证据、Token与Tool调用数、总耗时和终止原因放到同一请求记录中，使回归对比和
故障定位不再依赖进程内临时状态。

### 与 Agent 开发的关系

Run是Agent一次请求的外层观测单元：PageContext仍只是提示快照，业务事实继续来自Java Tool；Router结果经过严格Schema
后才能保存，模型与各组件版本继续引用不可变快照，终态指标由确定性生命周期服务一次提交。未调用模型时Token为0，
未经过统一路由时Router为空，迁移前记录不补造新字段，保证可观测数据不会反过来制造虚假执行事实。

### 可能的面试问题

**为什么版本快照和Token、Tool调用数要分开记录？**

回答要点：版本快照说明“这次运行绑定了哪套执行契约”，Token和调用数说明“这次实际执行用了多少资源”；配置存在不
等于组件被调用。分开记录才能避免把已配置模型冒充实际模型调用，也方便分别定位版本漂移和运行成本变化。

**为什么历史Run的页面、路由、耗时和终止原因保持空值，而Token与Tool计数回填0？**

回答要点：迁移无法恢复过去没有采集的上下文和耗时，填当前值会制造审计事实；计数字段为数据库非空约束提供0基线，
但历史版本状态仍明确标记不可恢复，查询方必须结合版本和字段可用性理解，不能把0解释成已证明当时没有调用。

## M7.2 Step完整类型：用稳定分类还原Agent内部执行路径

### 解决的问题/对项目的价值

早期`CONTEXT/TOOL/RULE/LLM`只能解释固定诊断，不能准确表达路由、Agent选动作、规范检索、人工确认和真实写回。九种类型把这些职责分开，让失败定位、后续SSE事件映射和运行路径展示使用同一套稳定语义。

### 与 Agent 开发的关系

Step类型只描述“这一步在Agent链路中做什么”，不描述业务结果真假，也不产生权限。九种类型通过同一生命周期服务持久化并共用摘要脱敏与截断；Tool还是由注册表和权限门禁执行，写回还需要Approval和Java重新校验。没有实际加入统一Run的内部组件不会为了补齐类型而伪造Step。

### 可能的面试问题

**为什么要区分AGENT、LLM和TOOL Step？**

回答要点：LLM表示一次通用模型调用，AGENT表示模型输出经结构校验后形成的动作决策，TOOL是确定性代码实际读取外部事实。分开后才能判断失败在模型请求、决策校验还是业务调用，不能因为三者相邻就混成一步。

**为什么不为尚未接入统一Run的组件预先写Step？**

回答要点：Step是已发生动作的执行证据，而不是功能清单。没有共享Run、顺序和生命周期时强行写入会制造虚假路径或序号冲突；应先由统一编排分配Run和Step顺序，再在真实调用边界记录。

---

## M7.3 SSE事件服务：把长链路执行进度安全地送到页面

### 解决的问题/对项目的价值

诊断和写回会跨越多个Tool、RAG及数据库步骤，单个同步HTTP响应无法解释中间在做什么，断线后也缺少续接位置。M7.3用
稳定事件类型和流内序号把执行进度实时推送给页面，并以心跳、短期回放和订阅清理降低长连接假死、重复展示和资源泄漏风险。

### 与 Agent 开发的关系

事件发布点覆盖路由、澄清、Agent动作、Tool、RAG、诊断、Approval和写回，但载荷只保留状态、数量和受控标识，不复制
用户原文、规范正文、审批草稿或Tool原始输出。SSE是面向交互的短期观察通道，数据库Run/Step才是持久审计记录，Java
继续裁决业务事实；当前内存流明确不声称支持跨Agent实例回放。

### 可能的面试问题

**为什么客户端要先建立stream_id连接，再发诊断请求，而不是等POST返回run_id后再订阅？**

回答要点：同步POST返回run_id时执行已经结束，无法接收中间事件。客户端先生成不可预测的流标识并完成连接，再把它放入
请求头，后端创建Run后通过首条`run_started`告知真实run_id；用户归属校验防止流标识被跨用户复用。

**Last-Event-ID为什么不能保证进程重启或跨实例后继续回放？**

回答要点：当前事件历史是有上限、有保留时间的单进程内存队列，`Last-Event-ID`只解决同一实例上的短暂断线。长期审计由
Run/Step数据库承担；若要跨实例无缝续接，需要外部事件Broker或持久事件表、全局序号和实例路由，这属于后续扩展边界。

**为什么SSE事件不能直接携带完整Tool结果和审批草稿？**

回答要点：事件可能被代理缓存、浏览器调试工具观察或重复回放，复制原始载荷会扩大敏感数据面并形成第二份事实。页面只需
阶段、状态、计数和安全身份来展示进度，最终业务结果仍从严格HTTP响应读取，事实与审计分别由Java和Run/Step负责。

## M7.4 前端实时步骤展示：把事件协议收敛为可恢复的用户交互

### 解决的问题/对项目的价值

后端能够发布事件并不等于用户能理解执行进度。前端SSE Client、纯时间线归并器和展示组件把分块网络数据变成有顺序、可去重、可定位失败且带耗时的步骤，用户可以区分“连接断了”和“业务执行失败”，排障也不必只看最终错误。

### 与 Agent 开发的关系

页面先建立用户隔离事件流再触发Agent执行，确保能观察从Run开始到终态的完整路径；重连只按后端允许的`Last-Event-ID`短期回放，非法事件关闭失败，不让未知数据进入界面。归并器只解释状态摘要，最终诊断仍由HTTP响应提供、业务事实仍由Java裁决，因此可观测通道不会成为新的事实来源或执行权限。

### 可能的面试问题

**为什么不用浏览器原生EventSource，而使用Fetch读取ReadableStream？**

回答要点：当前开发身份和断线续接需要显式发送`X-User-Id`、`X-User-Role`及`Last-Event-ID`，原生EventSource不能设置这些自定义Header。Fetch可以保留同源流式读取，同时让连接身份、超时、错误响应和重连策略由客户端明确控制。

**为什么要等SSE返回connected后再发送诊断POST？**

回答要点：如果两者并发，诊断可能在订阅真正建立前就发布首批事件，页面会遗漏Run开始或快速Tool步骤。先确认连接再用同一`stream_id`触发执行，可以建立清晰的先后关系；诊断不带流标识时仍保留原同步HTTP兼容路径。

**时间线为什么使用纯归并函数而不是在Vue组件里直接修改步骤？**

回答要点：重连会回放旧事件，网络分块也可能让事件到达节奏变化；纯函数按序号排序去重，再把开始/完成配对，可以对同一事件集合稳定得到相同UI状态，便于独立测试。Vue组件只负责渲染和运行中计时，不承担协议正确性或业务裁决。

## M7.5 Run历史页面：把持久观测数据变成可追溯执行视图

### 解决的问题/对项目的价值

Run和Step已经记录执行终态、摘要和耗时，但没有安全查询与页面组织时，用户刷新后仍只能查数据库或依赖当次响应，规范引用、人工修改和失败位置也散落在不同记录里。M7.5用列表、详情、Step接口及双栏页面把这些历史证据串起来，让用户能从一次Run继续查看诊断结果、执行步骤、Approval差异和错误原因。

### 与 Agent 开发的关系

三个接口都通过Run所属Session的`user_id`建立所有权边界，详情和Step不会因为调用方知道`run_id`就越权读取。服务层只恢复符合当前Schema的诊断和Approval草稿，Tool仅返回持久化时已经脱敏截断的摘要；Web再把Step类型、引用和字段差异转换成可读时间线。页面展示的是当次Agent执行证据，订单或任务ID不能替代Java当前事实，也不会带来Tool调用或写操作权限。

### 可能的面试问题

**为什么Run表没有user_id，列表仍能实现用户隔离？**

回答要点：Run通过`session_id`外键属于Session，Session保存创建用户；查询必须联表并在SQL中限制`AgentSession.user_id`，不能先查全部Run再在Python中过滤。这样未授权数据不会进入应用内存，总数也不会泄露其他用户的记录规模。

**为什么列表不直接返回final_result、page_context_snapshot和version_snapshot？**

回答要点：列表一次会返回多条记录，大字段会增加带宽和敏感信息面，而且用户浏览历史时只需要身份、状态、资源提示、耗时和错误。诊断结果由详情接口按单个Run重新授权并进行Schema恢复；页面上下文和版本快照仍不下发，因为它们是内部执行证据而不是页面需要展示的当前事实。

**为什么排序同时使用created_at和run_id？**

回答要点：只按时间排序时，同一数据库时间精度内创建的多条Run顺序可能不稳定，翻页会出现重复或遗漏；追加唯一`run_id`作为确定性次排序键，可以在数据集合不变时保持稳定。当前仍是offset分页，并发新增Run时页边界可能移动，规模增长后可升级为基于这两个字段的游标分页。

**为什么Tool输入输出只展示摘要，不直接展示完整JSON？**

回答要点：完整请求与响应可能包含大字段、敏感信息或会被误认为当前业务事实，也会在浏览器和代理中形成第二份数据副本。Step生命周期在落库前已经对白名单摘要做空白压缩、凭据遮盖和长度限制，历史接口只投影该摘要；需要确认当前业务状态时仍应重新调用受权限控制的Java Tool。

**Approval修改为什么同时保留模型原稿、用户最终稿和字段差异？**

回答要点：只保留最终稿无法说明哪些内容由模型提出、哪些由用户授权修改，只保留原稿又不能证明实际写入意图。两份不可变草稿加确定性字段差异能够清楚划分模型建议与人工责任，规范引用也随最终有效草稿展示；历史页只读，不会再次触发写操作。

## M7.6-A 模型配置：把“准备了环境变量”和“模型已启用”分开

### 解决的问题/对项目的价值

过去Compose传入的模型地址和密钥没有进入Settings，任意Provider字符串和单独一个模型名仍可能被版本快照描述为已配置。
T749建立明确启用条件，使配置错误在模型调用前暴露，同时保留模型关闭时固定诊断和其他非模型接口可运行。

### 与 Agent 开发的关系

模型Provider是Router、Action、RAG归纳和Review草稿的共同上游。统一配置契约让后续Client只接收经过校验的Provider、
模型名和地址；API Key使用`SecretStr`，且地址和密钥不会进入Run版本快照。配置就绪仍不代表发生过模型调用，实际调用
次数、Token和失败必须由后续LLM Step记录。

### 可能的面试问题

**为什么用MODEL_NAME作为显式启用开关，而不是检测API Key是否存在？**

回答要点：部署系统可能提前注入地址或密钥，也可能使用无密钥的本地网关。模型名为空能稳定表达“当前不启用模型”，
避免预置凭据被误认为运行能力；启用后再强制要求Base URL保证请求可寻址。

**为什么Base URL必填，而API Key允许为空？**

回答要点：所有OpenAI兼容调用都必须有明确目标地址，但本地Ollama或内部网关可能不需要鉴权。密钥是否必需由部署目标
决定，存在时必须作为SecretStr处理，不能通过日志或版本快照泄露。

**模型配置完成后为什么还不能声称系统已经接入模型？**

回答要点：配置只证明参数满足启动契约，不证明网络可达、结构化输出合法或某次Run实际调用过模型。必须等HTTP Client、
适配器和LLM Step接线后，才能用真实请求、Token和步骤记录证明模型参与了执行。

## M7.6-A 模型能力查询：安全公开配置状态而不冒充运行事实

### 解决的问题/对项目的价值

页面和部署检查需要知道模型是否按完整契约启用，但直接读取环境或打印Settings会扩大密钥泄露面，单看服务健康又无法区分
固定流程可用与模型已配置。T750用稳定只读响应公开配置状态和非敏感模型身份，为后续统一Agent入口提供前置能力判断。

### 与 Agent 开发的关系

能力服务把内部Settings投影为严格Schema：启用时必须同时返回Provider和模型名，关闭时二者必须为空；Base URL和API Key
从结构上不存在。查询不主动探测供应商，也不产生LLM Step，因此`configured=true`只能说明配置就绪，不能作为模型实际
参与路由、生成或草稿的证据。

### 可能的面试问题

**为什么能力接口不能在请求时顺便调用模型做健康检查？**

回答要点：配置查询应快速、确定且无外部副作用；如果绑定供应商网络，页面初始化会受模型限流、超时和费用影响，还会把
“配置存在”和“当前网络可达”混为一谈。真实调用健康、错误和Token应由后续模型Client与LLM Step单独观测。

**为什么模型关闭时不返回默认Provider？**

回答要点：默认Provider只是进程支持的协议，不代表存在一个可使用的模型。关闭状态将Provider和模型名同时置空，可以避免
调用方根据协议名误判为可执行；如果未来要公开“支持哪些Provider”，应增加独立字段和契约，不复用当前激活状态。

## M7.6-A 结构化模型Client与LLM Step：让真实调用可校验、可限流失败、可审计

### 解决的问题/对项目的价值

只有模型配置而没有公共调用边界时，Router、动作决策、问答和草稿生成会各自处理HTTP、JSON、重试和供应商异常，容易产生行为不一致、无限重放或把错误正文带入日志。T751～T753建立一个严格结构化Client和统一观测包装器，使合法输出与稳定失败都可由本地Stub重复验证，并让未配置模型不影响固定诊断启动。

### 与 Agent 开发的关系

Client要求模型正文继续通过调用方Pydantic Schema，模型只能交付候选结构，不能绕过后续确定性参数、权限、事实和引用门禁。瞬时网络、超时、限流和5xx只在小预算内重试，鉴权、参数、响应契约和输出Schema错误立即失败；LLM Step独立保存模型名、Token、耗时和实际重试次数，但不保存Prompt、模型正文、密钥或供应商错误正文。当前公共Client尚未适配四类业务Protocol，因此这些记录能力不会被冒充为统一Agent生产接线已经完成。

### 可能的面试问题

**为什么结构化输出既要向供应商发送JSON Schema，收到正文后还要再做Pydantic校验？**

回答要点：`response_format`只是对供应商的生成约束，不能替代本地信任边界；兼容网关可能忽略参数、模型可能返回非法内容，代理也可能改变响应。应用必须在进入Router或Workflow前重新校验，拒绝额外字段、类型强转和业务范围外的枚举值。

**哪些模型失败可以重试，为什么非法JSON不能重试？**

回答要点：超时、连接错误、限流、408/425和5xx可能是短暂故障，可以在明确次数与退避上限内重试；鉴权、参数、响应外壳及输出Schema错误通常不会因立即重放而改变，重试只会增加费用和延迟。更高层若要对模型内容纠错，应使用带新Prompt的显式业务策略，不能混入HTTP重试。

**为什么LLM Step要用独立列保存Token和重试次数，而不是拼进输出摘要？**

回答要点：摘要会脱敏、截断并面向人读，字符串解析无法保证类型、总量一致性或后续聚合。独立非负字段和总Token等式约束能支持查询、评测和告警；历史记录保持空值，不为过去没有采集的调用补造指标。

## M7.6-B 模型协议适配：把结构校验与业务授权分成两道门

### 解决的问题/对项目的价值

公共Client只能证明模型返回了符合JSON Schema的结构，不能证明其中的订单、动作、引用、候选或草稿事实真实且获准使用。五个独立适配器复用统一模型协议，同时保留原组件的业务白名单校验，防止“结构合法”被误当成“业务可信”。

### 与 Agent 开发的关系

Router和Action的模型输出先经过实体证据与只读Tool注册表校验；规范回答只能引用检索阶段提供的citation_id；Rerank必须覆盖全部候选且不能替换身份；Review模型只生成严格草稿，不获得Tool、Approval或写入能力。这体现了Agent系统中模型负责提出候选、确定性代码负责授权与落地的分层，也让不同Prompt可以独立版本化和测试。

### 可能的面试问题

**为什么通过Pydantic Schema校验后，还要再做业务门禁？**

回答要点：Schema只约束字段、类型和枚举，无法证明实体来自用户消息、动作已注册、引用确实来自本轮检索，或草稿仍指向诊断中的事实。第二层白名单和关联校验负责业务真实性与权限，二者不能互相替代。

**为什么为五种Protocol分别写适配器，而不是一个通用Prompt调用器？**

回答要点：五种任务的输入证据、输出Schema和失败门禁不同；分离后每个适配器只做协议转换，Router、RAG和Approval语义不会互相泄漏，Prompt版本、测试和后续替换模型也能独立演进。HTTP重试和供应商错误仍由公共Client统一处理。

**Review草稿模型为什么不能直接获得Tool或Approval Store？**

回答要点：草稿是待审查建议，不是写入授权。模型若同时持有执行能力，会把生成和授权合并，绕过人工确认与Java重新校验；因此适配器只返回严格ReviewDraft，持久化和执行必须经过后续确定性Workflow与确认服务。
