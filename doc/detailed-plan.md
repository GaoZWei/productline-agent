# 遥感数据产线 Agent 细化开发计划

## 一、任务拆分标准

每个开发任务尽量满足以下条件：

1. 单个任务预计耗时 1～4 小时；
2. 只修改一个明确模块；
3. 有固定输入和预期输出；
4. 至少包含一个自动化测试；
5. 有独立测试命令；
6. 完成后可以提交一次 Git Commit；
7. 不依赖尚未实现的大量后续能力。

单个任务的完成流程统一为：

```text
阅读接口或业务定义
→ 编写测试
→ 实现功能
→ 运行局部测试
→ 运行代码质量检查
→ 检查并同步当前 Mx.y 的“解决的问题”和“核心作用”
→ 更新 STATUS.md
→ 提交代码
```

“解决的问题”和“核心作用”统一按以下口径编写：

1. `解决的问题`用2～3句，先用实际场景说明缺少本阶段会出现的困扰或风险，再说明本阶段补上的能力；
2. `核心作用`用2～4句，依次说明本阶段在整体链路中的位置、接收的输入、完成的处理、交给下游的结果和关键边界；
3. Tool、Workflow、RAG、RRF、Rerank、Approval等术语首次出现时，要结合当前业务解释其实际含义，不只堆砌缩写；
4. 每次开发完成时同步复核两段说明，确保内容具体、通俗并与实际实现一致；事实、职责、边界或表述清晰度变化时
   及时修正，不写测试数字、文件清单或尚未实现的能力。

## M0.2 业务领域模型设计

### 解决的问题

如果订单、生产任务、质检问题、复核和交付在不同代码里各自解释状态，同一个订单可能同时被判断为“可交付”
和“仍待复核”。本阶段在Java业务层统一对象关系、状态枚举和状态约束，让系统先有一套明确、可执行的业务规则，
再对外提供接口。

### 核心作用

它位于数据库和所有上层能力之间，负责把数据库记录组织成有业务含义的订单、任务、问题、复核和交付对象。
Java接口和Python Tool都只能使用这些统一状态，上层模型可以解释事实，却不能决定某个状态组合是否合法；
最终合法性始终由业务领域规则裁决。

### 核心枚举

```text
BLOCKED
```

#### 质检问题状态


#### 复核状态

```text

```

#### 交付状态


## M0.3 固定业务数据

### 解决的问题

如果演示数据会随时间、随机数或测试顺序变化，同一句诊断请求今天和明天可能得到不同结果，出错后也难以判断
是代码回归还是数据变了。本阶段固定ORDER-001～005五种业务场景，并把ORDER-003的任务、质检、复核和交付
状态固化为可重置的黄金链路。

### 核心作用

这些固定数据是Java接口、Python Tool、诊断Workflow和跨服务测试共同使用的“标准试题”。上游重置脚本提供
相同业务快照，下游模块据此比较预期阻塞阶段、根因和建议，从而快速定位哪一层发生回归。固定数据只服务开发
和验收，不代表生产数据来源。

## M0.4 Java 查询接口

### 解决的问题

Python如果直接查询Java业务表，就会绕过资源归属、状态语义和权限检查，数据库结构一变还会拖垮Agent层。
本阶段为订单、任务、进度、质检、复核和交付提供稳定的Java只读API，让外部调用者通过业务接口获取事实，
而不是理解或拼接底层表结构。

### 核心作用

它是业务事实离开Java服务的唯一出口：接收资源ID和调用身份，完成存在性、归属和权限检查，再返回结构化业务
数据给Python Client和Tool。后续Workflow只能基于这些响应归纳诊断，不能绕过API读取表，也不能让模型补造
缺失的订单状态。

## M0.5 Java 写接口

### 解决的问题

复核提交和返工创建会真实改变业务数据，如果只按模型给出的参数直接写入，可能出现越权、重复提交或覆盖别人
刚刚修改的任务。本阶段在Java中提供受保护的写接口，并在事务内校验权限、当前状态、目标版本、幂等键和
操作日志。

### 核心作用

它位于人工确认链路的最终落库端：上游将确认后的复核或返工请求交给Java，Java重新读取最新事实并决定能否
提交，然后原子更新业务数据和审计记录。Python只能调用这项能力，不能代替Java判断写入是否合法；当前接口
本身也不代表Agent已经获得自动执行权限。

| ---- | --------- | ----------------------------- | --------- | -: |

## M0.6 Java 统一异常

### 解决的问题

如果Java接口有时返回文本、有时返回不同JSON，Python就只能根据HTTP状态或报错文案猜原因，也无法判断一次
失败是否值得重试。本阶段统一成功与错误响应，明确错误码、可重试标识和Trace ID，把参数、权限、资源不存在、
业务冲突和系统故障区分开。

### 核心作用

它是Java和Python之间的失败翻译协议：Java把内部异常转换成稳定机器字段，Python Client再把这些字段映射为
Tool可识别的错误。后续重试、Workflow终止和页面提示都依赖这套分类，而不是解析自然语言错误；异常响应不会
携带敏感内部细节。

统一响应：

```json
{
  "success": false,
  "code": "BUSINESS_CONFLICT",
  "message": "当前任务状态不允许提交复核",
  "data": null,
  "trace_id": "trace-001",
  "retryable": false
}
```

| T038 | 定义统一响应结构           | `ApiResponse<T>` | 1h |
| T039 | 实现参数异常处理           | 400 映射           | 1h |
| T040 | 实现未认证和无权限处理        | 401、403          | 2h |

### 解决的问题

# 四、M1：Python Tool 层

## 目标

Python Agent 服务能够稳定调用 Java 接口。

本阶段仍然不让大模型自主选择 Tool。

---

## M1.1 Python 工程初始化

### 解决的问题

如果Python侧只有零散脚本，HTTP调用、数据库连接、日志和测试会各自初始化，后续Tool和Workflow很难共享配置
或稳定部署。本阶段搭建FastAPI应用、配置加载、异步数据库、迁移、日志和质量检查，让Agent能力运行在一个
正式服务中。

### 核心作用

这是Agent侧所有模块的运行容器：它接收环境配置，管理HTTP服务和数据库生命周期，并向Client、Tool、Workflow
及运行记录提供统一依赖。它只解决工程运行和可观测性问题，不读取Java业务表，也不生成诊断结论。

## M1.6 Tool 重试

### 解决的问题

网络抖动或短暂超时可能让一次正确的只读查询失败，但对参数错误、无权限或业务冲突反复调用只会放大压力。
本阶段为明确的瞬时只读失败增加次数有限的退避重试，并把不可重试错误直接返回给调用方。

### 核心作用

它包在Client调用外层，在同一次逻辑Tool调用内判断错误是否瞬时、是否只读以及是否还有重试预算，然后决定再次
请求或结束。下游仍只看到一条逻辑调用结果。确定性错误和写操作不进入这套自动重试，避免掩盖真实问题或造成
重复写入。

建议规则：

```text
连接失败：重试
读取超时：重试一次
Java 500：根据 retryable 决定
Java 400/403/404/409：不重试
响应 Schema 错误：不重试
```

## M1.7 重复调用检测

### 解决的问题

名称和规范化参数生成稳定指纹，在单次Run中识别完全相同的逻辑调用，同时保留显式刷新最新事实的入口。

### 核心作用

重新查询。

## M2.6 确定性诊断规则

### 解决的问题

Java接口只会告诉系统各对象当前是什么状态，不会直接回答“订单为什么卡住、应该先处理什么”。如果让模型临场
推断，同一组事实可能得到不同结论。本阶段把生产、质检、复核和交付状态整理成固定优先级规则，稳定判断订单
最早受阻的阶段。

### 核心作用

它是固定诊断链路的事实裁决层：上游提供强类型Java事实，规则按业务优先级输出唯一阻塞阶段、根因、字段证据
和建议，下游文案与API只能表达这个结果。事实互相冲突或缺失时规则会安全停止，不让模型猜测缺口，也不修改
任何业务状态。

### 示例规则

```text
存在 FAILED/BLOCKED 生产任务
→ PRODUCTION_BLOCKED

生产完成，但存在 OPEN 质检问题
→ QUALITY_REVIEW

质检问题已解决，但复核 PENDING
→ REVIEW
```

## M4.2 知识库数据模型

### 解决的问题

规范文件进入数据库后，如果文档身份、版本、适用范围和分块内容没有统一结构，关键词索引和向量索引就可能指向
不同版本或重复内容。本阶段为文档和Chunk建立严格Schema、数据库表和索引字段，统一保存生命周期、权限、章节、
正文、全文检索内容和向量身份。

### 核心作用

它承接M4.1的规范目录，把文件级元数据和可检索片段映射到Agent自有知识库，为Loader、Embedding以及两路检索

## M4.8 混合检索

### 解决的问题

关键词分数和向量相似度不是同一种尺度，直接相加没有可靠含义；同一个Chunk还可能被两路同时召回，重复占用
结果位置。本阶段使用RRF按各通道名次进行融合，统一去重并合并同文档中的相邻片段，得到一组顺序稳定的候选。

### 核心作用

它位于初步召回和Rerank精排之间：接收已通过安全过滤的两组候选，用“倒数排名加权”的RRF合成统一顺序，同时
保留原始分数、各路排名和全部Chunk身份。下游可以据此继续精排和构建引用；融合层只组合候选，不判断最终
语义相关性，也不生成回答。

把关键词检索和向量检索返回的两组候选，转换成一组统一、去重、顺序稳定、可以继续交给Rerank处理的结果。


第一版使用固定排名常数的RRF，避免直接比较或相加关键词分数与余弦相似度。

## M4.9 Rerank

## M4.12 RAG 评测

### 解决的问题

几次人工提问成功不能证明检索稳定，也看不出正确证据只是偶然出现在末尾还是经常排在前面。本阶段准备固定问题、
预期文档和完整章节标注，用同一批数据比较关键词、向量、RRF和Reranker，并保存脱敏失败信息用于定位回归。

### 核心作用

它位于RAG运行链路之外，接收四种策略的有序候选，按统一标注计算Hit@5、MRR和无关片段占比，回答“能否召回、
排得多靠前、混入多少噪声”。评测复用生产元数据过滤，并要求文档与完整章节同时匹配。可控替身只验证数据契约
和算法口径，不能替代真实Embedding或Reranker质量结论。

Hit@5 = Top 5中至少命中一次的用例数 / 总用例数
例如 50 条问题中，有 42 条能在前 5 个结果里找到正确章节：Hit@5 = 42 / 50 = 0.84
回答的问题：系统有没有把正确证据召回到用户可用的前五条结果中

MRR 会考虑第一个正确结果出现的位置
用例A：正确结果排第2位 → 0.5
用例B：没有正确结果     → 0
MRR = (0.5 + 0) / 2 = 0.25
回答的问题：正确证据通常排得有多靠前？

无关片段比例 = 所有返回结果中的无关片段数/所有返回片段数


准备 50 条标注问题。

## M5.2 动作模型

### 解决的问题

### 核心作用

## M5.3 LangGraph 动态图

### 解决的问题

动作模型只能给出“一步做什么”，还不能独立完成多轮诊断；若靠零散函数互相调用，校验、异常和停止条件很容易

### 核心作用

执行调用、合并事实、判断完成和收口异常。任何失败都沿显式分支结束，不会跳过校验直接生成完整结论。

```text
→ execute_action
→ save_observation
```

## M5.4 Agent 执行限制

### 解决的问题

动态循环如果没有硬限制，模型可能不断重复同一个查询、在没有新信息时继续消耗调用，甚至尝试未知或写入型Tool。
本阶段加入最大轮数、Tool调用预算、重复指纹、连续无新增信息、只读白名单和参数权限校验等确定性门禁。

### 核心作用

它包围M5.3的整个循环，在决策前检查预算、执行前检查动作和权限、Observation保存后检查是否真正获得新信息。
输入是当前State和待执行动作，输出是允许继续、拒绝执行或带明确原因的安全终止。所有限制由代码裁决，模型不能
通过Prompt响应提高预算或绕过写Tool黑名单。

## M5.5 信息充分度判断

### 解决的问题

不同订单所处阶段不同，需要补查的事实也不同；若让模型凭感觉判断“信息够了”，可能漏掉交付或质检事实，也可能
为了凑齐固定字段做无关查询。本阶段把基础必需信息和生产、质检、复核、交付、规范等场景条件写成确定性缺口规则。

### 核心作用

它位于每次Observation之后和下一轮决策之前，接收已验证的订单、任务及阶段事实，输出仍缺少的信息类型。缺口
既提示模型下一步可查询什么，也供确定性完成节点判断能否结束；只有当前场景必需事实齐全后才允许形成诊断。
该规则不改变固定Workflow原有的全量事实边界。

```text
交付状态
```

```text
质检异常 → 质检问题
复核异常 → 复核结果
规范判断 → RAG 结果
```

## M5.7 版本记录

### 解决的问题

如果Run只记录输入和结果，Prompt、模型参数或Tool Schema升级后，就无法还原历史诊断当时使用的是哪套配置，
也难以判断结果差异来自业务数据还是版本变化。本阶段为Router、动态Agent、Tool和RAG生成统一版本快照，并在
Run创建时冻结关联。

### 核心作用

它位于执行配置和持久化Run之间：应用启动时从代码常量、非敏感配置和真实Tool注册表生成快照，Run只引用该次
实际版本。下游排查可以据此区分Prompt、模型、Tool契约或RAG策略的变化。快照不保存密钥、完整Prompt和Tool
响应，迁移前无法恢复的版本会被明确标记而不是猜测。

## M6.1 Approval 数据模型

### 解决的问题

模型生成的复核建议不能直接写回业务系统，否则用户还没确认、目标版本已经变化或请求被重复提交时，都可能造成
错误操作。本阶段建立Approval持久化记录和状态机，分别保存原始草稿、用户修改、目标版本、待调用Tool以及

### 核心作用

Approval位于Agent草稿和Java业务写Tool之间，是“建议”变成“可执行请求”前的人工授权边界。它接收模型草稿
和目标对象信息，冻结原稿、记录修改与确认事实，并用确定性状态机输出后续是否具备执行资格。M6.1只建立记录
和生命周期，不调用任何业务写接口，也不把模型意见当作授权。

## M6.2 复核草稿 Schema

### 解决的问题

Approval可以保存通用JSON，但通用结构无法阻止非最终结论、过长文案、重复引用或“需要返工却没有返工类型”
这样的矛盾内容，也无法防止编辑时换掉目标任务。本阶段定义ReviewDraft及其嵌套Schema，把复核结论、问题摘要、
意见、规范引用和返工建议收紧为可校验草稿。

### 核心作用

ReviewDraft位于模型生成、用户编辑和后续写Tool参数映射之间：接收结构化复核内容，校验字段长度、结论与返工
关系、任务身份及引用去重，再向Approval提供规范化数据。它复用RAG Citation保留规范版本和Chunk来源，并提前
对齐Java写接口的文案限制。本阶段不判断引用此刻是否仍有效，也不执行Java写操作。

```json
{
  "task_id": "TASK-003",
  "conclusion": "REWORK_REQUIRED",
  "problem_summary": "存在未关闭的坐标系质量问题",
  "review_comment": "建议完成坐标系统处理后重新提交复核",
  "specification_references": [],
  "suggested_rework": {
    "required": true,
    "type": "COORDINATE_SYSTEM_FIX"
  }
}
```
